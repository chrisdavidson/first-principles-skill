## 2. Failure Causes (raw pre-mortem list, then clustered)

I wrote these without filtering, then grouped them. The adversarial question applied to each: *"Would I have glossed over this if reviewing my own code quickly?"*

### Cluster A — Error handling that *masks* the real startup error (highest signal)

This is the most common reason a startup crash is "impossible to figure out": your error handling is eating the diagnostic.

- **A1. Bare `except:` or `except Exception:` at module load / entrypoint** that catches the real `ImportError`/`NameError`/`FileNotFoundError`, then re-raises something generic or calls `sys.exit(1)` with a vague message. The true traceback is gone.
- **A2. Swallowed exception with `pass` or a logged-but-suppressed error** during config/connection setup — the script limps forward in a half-initialized state and crashes *later* on a `None`/`AttributeError` that points nowhere near the true cause.
- **A3. Logging the error before logging is configured.** If your `except` block calls `logging.error(...)` but logging setup itself failed (or runs after the failure), the message is silently dropped — you see a crash with no log line.
- **A4. `except` that references an undefined name** (e.g., logs a variable that was never assigned because the `try` failed early) — turning the original error into a confusing secondary `NameError` from inside the handler.

### Cluster B — Error handling that *is* the crash (runs at import time)

- **B1. Module-level (top-of-file) code wrapped in try/except that re-raises.** Anything at module scope — `client = SomeSDK(api_key=os.environ["KEY"])`, file reads, DB connects — runs on import. A `try/except` here that `raise`s on failure crashes before `main()` is ever called.
- **B2. `os.environ["VAR"]` (subscript, not `.get`)** at module level raises `KeyError` on startup if the env var is missing. A common "works on my machine" crash.
- **B3. Exception raised inside a decorator, default-argument expression, or class-body** — these evaluate at import time, and error handling placed in `main()` never gets a chance to run.
- **B4. Circular import surfacing as a confusing `ImportError`/`AttributeError`** that your top-level `try/except ImportError` catches and reports misleadingly.

### Cluster C — Entry-point / structural

- **C1. No `if __name__ == "__main__":` guard, or work done above it** — import-time side effects run during tooling/test collection and crash.
- **C2. `try` around the whole body with the `except` doing `sys.exit()`** — exit code looks like a clean crash; you never see *what* failed.
- **C3. Exception in `atexit`/`finally`/cleanup** that overrides the original exception (the original is chained but easy to miss if you only read the last line).

## 3. Recurring Pattern (the structural weakness)

Two of the three clusters point at the same root: **error handling positioned at module scope and/or written to suppress-and-replace rather than surface.** That is the structural weakness a quick self-review misses. The crash isn't "hard to find" — your handlers are deleting the evidence (A1–A4) or running before `main()`'s handlers can help (B1–B3).
