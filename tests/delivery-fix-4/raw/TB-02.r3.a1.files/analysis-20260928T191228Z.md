**Adversarial technique — Pre-Mortem** (headline conclusion is a plan/recommendation; decision rule routes here rather than to Inversion, whose Phase-2 invocation already ran).

*Premise:* It is six months later. The plan has already failed — CI duration and batching behavior are both effectively unchanged, and leadership is frustrated that the recommended data-first approach produced no visible improvement.

*Causes* (unfiltered, generated from four stakeholder viewpoints — platform/CI-infra team, developers, leadership/budget owners, on-call/incident-response):
1. (platform) The stage-timing diagnostic (C8) was never actually run because no one was explicitly assigned to own it.
2. (platform) The tiered-pipeline split (option C) was scoped as a multi-quarter re-architecture instead of an incremental first slice, and stalled in planning.
3. (platform) Selective testing or caching introduced false negatives / stale-cache bugs, causing a production incident that discredited "process fixes" generally.
4. (developers) Even after a fast-feedback tier shipped under ~10 minutes, developers had already built batching into habits/tooling and didn't revert (habit inertia exceeds the now-smaller CI pain).
5. (developers) The async full-suite tier started failing more often post-merge, uncoupled from a pre-merge block, so reverts became more frequent and confusing — developers batched *more* to avoid dealing with ambiguous post-merge failures.
6. (leadership) Leadership funded the runner purchase in parallel anyway as a hedge, diluting focus/budget and preventing the org from learning which intervention actually worked.
7. (leadership) The developer survey meant to test GT-10 (the batching motive) was never run because "we already know why," so the diagnosis step was skipped in practice despite being recommended.
8. (on-call) No one owned flaky-test triage or runner-concurrency capacity planning on an ongoing basis, so those bottleneck classes silently worsened as the team grew, offsetting gains elsewhere.
9. (cross-cutting) No revert/rollback policy was defined for post-merge full-suite failures before launch.

*Clusters:*
- **Cluster 1 — No owner, diagnostic never run** (causes 1, 7) — bears on C8, A20, A27.
- **Cluster 2 — Scope crept into a stalled re-architecture** (cause 2) — bears on C5's engineering-effort criterion for option C.
- **Cluster 3 — The fix itself introduces new failure modes that erode trust** (causes 3, 5, 9) — bears on C5's new-risk criterion (why option C scored only 3/5, not 5/5) and on C7.
- **Cluster 4 — Behavioral habit inertia: technical fix arrives, behavior doesn't reverse** (cause 4) — bears directly on C2 and C7.
- **Cluster 5 — Hedged/parallel spending prevents learning** (cause 6) — bears on C5, whose entire purpose is to make a reasoned choice rather than hedge indiscriminately.
- **Cluster 6 — Externalized, unowned bottleneck classes keep degrading** (cause 8) — bears on GT-3, GT-4, A9, A21.

*Disposition:*
- Cluster 1 — **plan change:** assign one named owner (CI-infra lead) and a dated deliverable ("stage-timing + queue + retry breakdown within 2 weeks") as a gate before any spend is approved.
- Cluster 2 — **plan change:** scope the tiered-pipeline work as an incremental first slice (e.g., split out lint+unit into a fast tier within ~3 weeks); defer full re-architecture; re-score in C5 if the incremental slice proves undeliverable that fast.
- Cluster 3 — **accepted risk, named mitigation:** accept that any pipeline change carries some new-failure-mode risk (already priced into C5's new-risk score); mitigate with an explicit revert/rollback SLA and an on-call alert path for post-merge "full tier red," defined before launch.
- Cluster 4 — **accepted risk, named mitigation:** accept that behavior change lags technical change; mitigate by pairing the technical fix with an explicit team norm reset (diff-size guidance informed by GT-5's 200–400 LOC finding), not assuming the technical fix alone reverses the habit.
- Cluster 5 — **plan change:** make the trade-off ranking (C5) an explicit go/no-go input to budget approval; do not fund option A in parallel as a hedge before Cluster 1's diagnostic completes; revisit option A with data if the diagnostic shows a compute-bound pipeline.
- Cluster 6 — **plan change:** assign explicit, ongoing (not one-time) ownership for flaky-test triage and runner-concurrency capacity planning, tied to A20/A21.

*Falsification.* This analysis's headline conclusion is false if a stage-by-stage timing breakdown shows the pipeline is predominantly (say, >70%) compute-bound, with negligible queue-wait, negligible flaky-retry time, and no heavy mandatory non-compute gate — in that specific case, buying faster runners would in fact be the correctly-targeted, high-leverage fix, and this analysis's "insufficient/dominated lever" verdict would not hold.

## 1. Problem Essence

**Core problem:** Will replacing the CI runner hardware with faster machines eliminate — or materially reduce — the developer behavior of batching changes to avoid pipeline pain, or does the evidence point to a different binding constraint (queueing/concurrency, I/O-bound steps, flaky-retry overhead, or the psychological/attentional cost of any non-trivial feedback delay) that hardware alone cannot fix?

**Success criteria:**
1. Names which bottleneck class(es) — compute-bound, I/O/external-service-bound, queue/concurrency-bound, flaky-retry-bound — plausibly dominate the 47 minutes, or states precisely what data would confirm this.
2. States precisely what faster runners can and cannot address, mapped to those bottleneck classes.
3. Determines whether wall-clock duration itself, versus some other mechanism (attention/interruption cost, blast-radius fear, review friction), is the more defensible causal driver of batching, and flags this as unresolved if the evidence doesn't settle it.
4. Derives a theoretical floor for pipeline duration that is independent of runner speed.
5. Compares buying faster runners against named alternative interventions on a locked, weighted cost/effectiveness basis.
6. Assesses whether batching itself carries second-order costs (review effectiveness, change stability, blast radius) that persist regardless of what happens to CI duration.
7. Delivers one clear verdict (right call / partial-insufficient / wrong lever) with a concrete, prioritized recommended action set, and names the specific data needed to confirm the diagnosis before further spend.

## 3. Ground Truths

- **GT-1** A pipeline whose stages have sequential dependencies has a wall-clock floor equal to at least the sum of the durations of the steps on its critical (necessarily-sequential) path; steps whose duration is fixed by something other than compute speed — network round-trip time, external-service response time, fixed sleep/wait/approval gates — cannot be shortened by faster compute, no matter how much is spent on it. — source: critical-path scheduling theory / Amdahl's Law (Amdahl, 1967); provenance: **definitional** (deductive mathematical/logical fact, not an empirical claim requiring a source read).
- **GT-2** Runner compute speed (CPU/memory throughput) reduces the duration of compute-bound work roughly in proportion to the speedup, but has no effect on I/O-bound wait (network calls, artifact transfer, external service latency), queue-wait time before a job is scheduled, or fixed-duration gates. — source: computer-systems architecture (definition of what "runner speed" changes vs. does not change); provenance: **definitional**.
- **GT-3** Flaky-test retries add variable, non-deterministic time to a pipeline run driven by test non-determinism or environment instability, not by insufficient compute; a faster runner speeds up the retry's own execution but does not reduce the number of retries triggered. — source: CI/testing-systems definition of retry semantics; provenance: **definitional**.
- **GT-4** When job arrival rate approaches or exceeds available concurrent-runner capacity, wait-before-start time is governed by concurrency (number of parallel runners/executors), not by individual runner speed; increasing per-unit speed without increasing concurrency does not reduce queue wait for jobs stuck behind other jobs. — source: queueing theory (M/M/c model); provenance: **definitional**.
- **GT-5** In the SmartBear-documented Cisco Systems code review study, review effectiveness is highest for diffs of 200–400 lines of code reviewed over 60–90 minutes, yielding 70–90% defect discovery; defect-detection rate falls as reviewed diff size grows beyond that range. — source: SmartBear, "Best Practices for Peer Code Review," https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/; provenance: **read-at-source** (quoted directly: "developers should review no more than 200 to 400 lines of code (LOC) at a time"; "a review of 200-400 LOC over 60 to 90 minutes should yield 70-90% defect discovery").
- **GT-6** Smaller batch sizes of change are associated with improved change stability and are, per DORA's own published guidance, "easier to recover from if there's a failure." — source: dora.dev, "DORA Metrics: The Four Keys," https://dora.dev/guides/dora-metrics-four-keys/; provenance: **read-at-source** (quoted directly: "Smaller changes are easier to rationalize and to move through the delivery process. Smaller changes are also easier to recover from if there's a failure.").
- **GT-7** The widely-adopted "ten-minute build" convention (originating in Extreme Programming practice) holds that CI feedback should complete in roughly ten minutes, because build/feedback delay directly costs developer time on every commit and "sucks the blood" out of the practice of integrating frequently; this is presented in the source as a broadly-achieved industry benchmark ("most of our modern projects achieve this"), not a hard physical limit. — source: Martin Fowler, "Continuous Integration," https://martinfowler.com/articles/continuousIntegration.html; provenance: **read-at-source** (quoted directly: "the XP guideline of a ten minute build is perfectly within reason"; "Nothing sucks the blood of Continuous Integration more than a build that takes a long time.").
