**What it ruled out:** Any recommendation to decompose immediately "to save a rewrite later." The future-optionality criterion in the C5 trade-off, which modular monolith wins on, already captures the legitimate part of this instinct without paying the network-boundary cost now.

### Dead End: Build for anticipated scale now (anticipatory scaling)

**What was tried:** Considered recommending microservices as insurance against future load growth, reasoning that re-architecting under load pressure later is harder than building for scale from the start.

**Why abandoned:** Contradicted by GT-2's monolith-first evidence (the same boundary-discovery risk applies) and by GT-5's Segment case, which documents the opposite failure mode: over-decomposition creating its own operational crisis (three engineers full-time just keeping 140+ services alive) rather than preventing one.

**What it ruled out:** Any recommendation grounded in "scale before you need to." Chain C1's Fermi estimate independently shows no scaling pressure exists at 1,200 DAU, so this path would have been premature optimization even before GT-2's boundary-risk argument is applied.

### Dead End: Reorganize the six engineers into per-service sub-teams to satisfy Conway's Law and unlock microservices

**What was tried:** Considered whether splitting the existing six-person team into smaller per-service sub-teams (e.g., three pairs of two) would resolve chain C3's team-boundary objection and make microservices viable.

**Why abandoned:** A sub-team of two engineers is far below GT-4's documented minimum (eight single-site / six multi-site) for sustaining even one on-call rotation; splitting the team would make the C2 objection worse, not better, since each sub-team would separately fail the on-call-capacity must-have that already knocks out full decomposition in chain C5.

**What it ruled out:** "Reorganize first, then decompose" as a way around the operational-capacity constraint. It shows the constraint is a headcount-level limit (GT-4), not merely a structural one, so no reorganization of the same six people resolves it.

## 6. Conclusion

**Recommended approach:** Do not adopt a microservice architecture now. Keep the product on a single deployable, but refactor it into a modular monolith with enforced internal module boundaries, and adopt narrow single-component extraction only for a component with a genuinely divergent resource profile if one emerges (chain C5).

**Recommended approach — implementation notes:**
- Enforce module boundaries with build-time or lint-time dependency-direction checks, not documentation alone (chain C5).
- Define explicit, numeric re-evaluation triggers now rather than leaving "later" vague: DAU sustained above roughly 50,000 for two or more weeks, peak sustained request load above roughly 500 requests/second for a month, engineering headcount above roughly 12-15, or a named subsystem's resource profile diverging from the rest by more than roughly 5x (chain C2).

**Key insight:** The naive framing "microservices vs. monolith" hides the actual binding constraint, which is not the code's structure but the team's on-call capacity: this team is already at or below the minimum headcount documented for sustaining even one 24/7 on-call rotation, so the real question a microservices decision must answer here is a staffing question before it is an architecture question (chain C2).

**Trade-offs acknowledged:** This recommendation defers the option of true per-service independent scaling and per-team deployment autonomy, and it accepts that a modular monolith gives weaker workload isolation (a bug in one module can still affect the whole process) than full decomposition would — a risk this analysis accepts with the named mitigation of isolating any genuinely divergent-workload component into its own process within the same deployable rather than a full service split (chain C5).
