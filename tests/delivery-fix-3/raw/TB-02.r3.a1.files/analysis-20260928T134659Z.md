# 3. Ground Truths

- **GT-1** Amdahl's Law: for a process split into a non-accelerated fraction *s* and an accelerated fraction *(1-s)*, total time T(n) = T·s + T·(1-s)/n as the accelerated fraction is sped up by factor n; as n→∞, T(n)→T·s. Speeding up only the accelerated portion can never reduce total time below the non-accelerated fraction's own duration. — source: Amdahl, G.M. (1967), standard parallel-computing identity; read-at-source: derivation shown inline above (mathematical identity, verified by direct algebraic substitution, not an external document claim).
- **GT-2** In a shared queueing system, when job arrival rate approaches the system's total service capacity (number of concurrent servers × per-server throughput), expected wait-before-service grows non-linearly and is governed by concurrency and arrival load, not by the speed of any single server (M/M/c waiting-time / Erlang-C behavior). — source: standard queueing theory; read-at-source: derivation shown inline above (mathematical identity).

**What was tried:** considered substituting a plausible-sounding industry split (e.g., "test execution is typically X% of CI time") for the missing breakdown, so the analysis could produce a numeric answer instead of a conditional one.

# 6. Conclusion

**Recommended approach:** Gate any CI-runner hardware purchase on a short, near-zero-cost measurement phase — per-stage pipeline timing plus runner queue-wait metrics, run for 1-2 weeks — and a brief developer survey on why they batch; in parallel, start the three levers chain C6 ranks above hardware speed (runner-pool autoscaling/queue-concurrency fixes, build/dependency caching, and test parallelization/sharding) and adopt a workflow change (merge queue / smaller stacked PRs) that directly targets the non-latency drivers of batching chain C3 identifies; treat buying faster runners as justified only if the measurement phase shows the critical path is dominated by already-maximally-parallel, non-cacheable, single-threaded compute (chain C7).

**Key insight:** Reasoning by convention jumps straight from "the pipeline is slow" to "buy faster hardware." First-principles decomposition shows the 47-minute figure is compatible with several structurally different bottlenecks that faster individual runners do not equally address, and that the batching behavior leadership actually wants to fix is driven at least partly by factors — blame-risk, flaky-retry pain, context-switch cost — that raw latency reduction does not touch. The proposed fix targets the announced symptom (pipeline minutes) more directly than it targets the actual problem (batching and its downstream costs) (chain C1, chain C3).

**Trade-offs acknowledged:** This recommendation defers a single decisive purchase decision, asks leadership to accept roughly 1-2 weeks of measurement latency before any spend, and treats three levers as a roughly-tied cluster rather than picking one winner — the flip test on chain C6 shows this is a genuine near-tie (a one-point weight shift on a single criterion reorders the top three), not manufactured indecision, and the cluster's internal ordering should be set by what the measurement phase finds (chain C6).
