## 3. Ground Truths

- **GT-1** In a DAG of dependent tasks, total duration is set by the longest chain of dependent (critical-path) activities; activities off the critical path have slack and shortening them does not shorten total duration — source: Wikipedia, "Critical path method"; read-at-source: "A critical path is determined by identifying the longest stretch of dependent activities..." and "Activities on subcritical paths have no drag, as they are not extending the project's duration."
- **GT-2** Amdahl's Law: S(s) = 1/(1 − p + p/s); as s → ∞, speedup approaches 1/(1 − p) — bounded by the non-parallelizable fraction regardless of added parallel resources — source: Wikipedia, "Amdahl's law"; read-at-source: the formula and "even with an infinite number of processors, the speedup is constrained by the unparallelizable portion."
- **GT-3** In an M/M/c queue, average response time = C(c,λ/μ)/(cμ−λ) + 1/μ, stable only while ρ = λ/(cμ) < 1; as arrival rate λ approaches total capacity cμ, response time grows sharply toward infinity, and total capacity is a function of server count c, not per-server speed μ alone — source: Wikipedia, "M/M/c queue"; read-at-source: the stability condition and response-time formula.
- **GT-4** Continuous-integration guidance holds that "a ten minute build is perfectly within reason" for most projects; the usual bottleneck for enterprise applications is testing, "particularly tests that involve external services such as a database"; teams reach fast builds mainly by spinning up "a small fleet of servers" and running tests in parallel — source: martinfowler.com/articles/continuousIntegration.html; read-at-source: quoted passages on the ten-minute build, the testing bottleneck, and fleet parallelization.
- **GT-5** Flaky tests are a recognized, significant problem at scale; they create noise that obscures whether real issues exist, undermine engineer confidence, and "intermittent failures cause engineers to take longer to submit" — source: testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html; read-at-source: quoted passages on flaky-test impact and mitigation.
- **GT-6** DORA's 2024 State of DevOps research names "small batch sizes" among the fundamentals that "remain crucial" to software delivery performance — source: dora.dev/research/2024/dora-report/; read-at-source: the passage naming small batch sizes among the fundamentals.
- **GT-7** Infrequent, large-batch integration produces "integration hell"; unpredictability grows with the amount of code and time between integrations; conflicts left undetected for weeks become very hard to resolve; frequent small commits instead make integration "a non-event," because only "a few hours of changes exist between commits, so there's only so many places where the problem could be hiding" — source: martinfowler.com/articles/continuousIntegration.html; read-at-source: quoted passages on integration hell, unpredictability, and diff debugging.
- **GT-8** GitHub-hosted runner pricing scales with compute class: 2-core Linux runs $0.006/min; larger runners range from $0.012/min (4-core) to $0.252/min (96-core) — a 48× core increase for a ~42× price increase, i.e., roughly proportional — source: docs.github.com/en/billing/reference/actions-runner-pricing; read-at-source: the quoted per-minute rate table.
