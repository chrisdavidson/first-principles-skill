# 3. Ground Truths

- **GT-1?** 9 client applications total consume the API; 3 of the 9 are mobile apps — unverified: stipulated by the requester as a fixed premise for this exercise; explicitly excluded from in-session verification (no codebase available).
- **GT-2?** Mobile screens require 4–6 round trips (sequential and/or parallel REST calls) to render a single screen — unverified: same reason as GT-1.
- **GT-3** A single GraphQL query can traverse nested/related fields and receive exactly the requested shape in one response, "instead of making several roundtrips as one would need in a classic REST architecture" — source: graphql.org/learn/queries/; read-at-source: the "Fields"/example-query section, quoted directly above.
- **GT-4** Naive GraphQL resolver implementations issue one backend/database call per field per returned item (the N+1 problem) unless batching (e.g., DataLoader) is used — source: github.com/graphql/dataloader; read-at-source: README passage "there could be at most 13 database requests" and the DataLoader definition, quoted above.
- **GT-5** HTTP/2 multiplexes multiple requests/responses concurrently over a single TCP connection, "fixing the HTTP-transaction-level head-of-line blocking problem in HTTP 1.x" — source: en.wikipedia.org/wiki/HTTP/2; read-at-source: Goals section, quoted above.
- **GT-6** The Backend-For-Frontend (BFF) pattern is a dedicated server-side layer, "tightly focused on a single UI," typically one per client type, that aggregates/tailors backend calls for that client — protocol-agnostic (works whether the client-facing edge is REST or GraphQL) — source: samnewman.io/patterns/architectural/bff/; read-at-source: pattern-definition passage, quoted above.
- **GT-7** JSON:API's sparse-fieldsets mechanism lets a REST client "request that an endpoint return only specific fields… by including a `fields[TYPE]` query parameter," without changing the underlying resource-oriented protocol — source: jsonapi.org/format/#fetching-sparse-fieldsets; read-at-source: quoted above.
- **GT-8** GraphQL has "no URL-like primitive" providing a globally unique cache identifier the way REST resource URLs do, so standard HTTP/CDN/browser caching does not apply the same way, requiring an application-level caching strategy — source: graphql.org/learn/caching/; read-at-source: quoted above.
- **GT-9?** Mobile/cellular network round-trip latency is generally higher and more variable than typical wifi/broadband, so a fixed number of sequential round trips costs disproportionately more wall-clock time on mobile than desktop — unverified: two WebFetch attempts (web.dev pages) did not surface a directly quotable authoritative figure within this session's budget; not pursued further. This ground truth is *not* load-bearing for any chain's head in this analysis — it only explains, informally, why the complaint in GT-2 originates from the mobile clients rather than the other 6.

# 5. Abandoned Reasoning

### Dead End: Treating server-side resource granularity as the sole explanation for the round trips
**What was tried:** attempting to conclude, from the fishbone brainstorm alone, that REST's fine-grained resource shape is *the* cause, and drilling five-whys down that single branch to a root cause.
**Why abandoned:** no network trace or codebase access was available this session to discriminate resource-granularity from client-side serial waterfalls (both remain live fishbone candidates); the five-whys drill on the granularity branch bottomed out at an actionable corrective (build an aggregation layer) at the same level regardless of which sub-cause dominates, making further drilling unnecessary for the recommendation, though it remains open for future investigation with an actual HAR trace.
**What it ruled out:** it saves a future analyst from re-litigating "which single cause is it" before acting — the recommendation is deliberately structured (C1, hop 3) to be robust to either answer, so resolving the ambiguity is useful for tuning implementation detail, not for choosing between Options A/B/C.

### Dead End: Recommending full replacement (Option A) on "GraphQL is the modern industry standard"
**What was tried:** considering a recommendation for Option A grounded in the observation that many large tech companies have adopted GraphQL.
**Why abandoned:** this is reasoning by analogy used as direct evidence, which the methodology bars — no ground truth about *this org's* situation supports it. Once tested against the ground-truth-anchored trade-off (C5), Option A scores 51 against 93/101 for the targeted options, and the robustness check shows this holds even when Option A's single best-scoring criterion is weighted to its ceiling.
**What it ruled out:** it saves a future analyst from re-proposing full replacement on adoption-trend grounds alone; any renewed case for Option A would need to change the underlying ground truths (e.g., a genuinely different cost structure or an org-wide multi-client-type expansion plan), not cite what other companies did.

### Dead End: Accepting "GraphQL fixes round trips" as sufficient justification and stopping there
**What was tried:** taking the complaint (GT-2) plus GraphQL's traversal capability (GT-3) as a complete argument for adopting GraphQL somewhere, without checking whether non-GraphQL mechanisms achieve the same effect.
**Why abandoned:** this is exactly the "too clean" conclusion the inversion-style challenge in Phase 2 exists to catch; GT-6 and GT-7 show the same client-facing outcome is reachable without GraphQL, converting the question from "GraphQL: yes or no" into "which aggregation mechanism, at what scope" (C2, C5).
**What it ruled out:** it saves a future analyst from treating "GraphQL solves it" as the end of the analysis rather than its starting observation.

# 6. Conclusion

**Recommended approach:** Do not replace REST with GraphQL wholesale; instead ship a targeted, protocol-agnostic aggregation layer for the mobile screens that need it — by default a REST aggregation/BFF layer (Option C), switching to a GraphQL BFF for mobile only (Option B) if the number of distinct mobile screen shapes needing aggregation is already large or growing fast (chain C5).

**Key insight:** The round-trip problem is caused by a missing aggregation/composition layer between resource-oriented REST and screen-oriented mobile needs, not by REST-as-a-protocol being inherently deficient — so "adopt GraphQL" treats one sufficient cure as if it were the only one (chain C1, chain C2).

**Trade-offs acknowledged:** A full REST-to-GraphQL replacement is ruled out primarily on cost and blast-radius grounds, bracketed at roughly 4–6x the engineering cost of a targeted fix for a problem only 3 of 9 clients have (chain C3); the targeted fix accepts some risk of aggregation-endpoint sprawl (Option C) or server-side fan-out and query-surface growth (Option B) that must be actively managed going forward (chain C5).

**Pre-check:** head C1 (MEDIUM), C2 (HIGH), C3 (LOW), C4 (MEDIUM), C5 (MEDIUM) · ?-marked: none directly, but GT-1?/GT-2? propagate through C1/C3/C4/C5 · lowest cited: LOW (C3) · Inputs ceiling: LOW
**Confidence:** LOW overall, by inheritance from C3's Fermi-range uncertainty (chain C3) — this LOW is a magnitude-precision rating, not a directional one. The *direction* of the recommendation (rule out A; favor C over B by default) rests on C1 (MEDIUM), C2 (HIGH), C4 (MEDIUM), and C5 (MEDIUM), none of which depend on C3's absolute numbers — C5's own robustness check (chain C5, hop 2) shows the Option-A-ruled-out result survives even without precise cost figures. Two named conditions flip the B-vs-C half of the recommendation: (1) the team already has material GraphQL fluency (assumption A-4), lowering Option B's learning-curve cost; (2) the mobile screen-shape count is already large or fast-growing rather than small and stable (assumption A-9), which erodes Option C's endpoint-per-screen cost advantage over time. A third condition would revive Option A specifically: if all 9 clients — not just the 3 mobile ones — are independently expected to need the same flexible, client-composable query capability within a similar timeframe, the amortized cost case for standardizing once (Option A) could outweigh building two separate targeted layers; this was not evaluated here because GT-1/GT-2 stipulate the complaint as mobile-specific and the other 6 clients as unaffected (assumption row 5).

**Premise:** The plan — ship Option C by default, with a named trigger to revisit Option B, having ruled out Option A — has already failed six months from now.

**Causes (unfiltered, from three stakeholder viewpoints):**
- *Mobile engineer:* the new aggregation endpoints were designed without mobile input and don't match what screens actually need, so mobile still makes several calls; the aggregation layer became "just another set of resources to keep in sync."
- *Backend/platform engineer:* nobody owns the new aggregation endpoints long-term, so they rot; every new mobile screen becomes a backend ticket, recreating the original bottleneck one layer up; endpoint count grew unchecked (the sprawl risk named in C5's second-order extension).
- *Product/business:* the fix shipped, round trips dropped, but the target metric (screen load time) didn't move, because round trips were never the dominant latency cost — payload size or client render time was (the unmeasured assumption "round trips are the dominant contributor…").
- *Ops/SRE:* the new aggregation endpoint became a single fan-out point — one client request now triggers several backend calls server-side (the same underlying dynamic as GT-4's N+1, applied to a hand-rolled REST aggregator) — and an unbatched version caused a load spike or cascading failure under mobile traffic that nobody load-tested for.
- *Architecture/process:* the "trigger condition to revisit Option B" (schema/endpoint-count threshold) was never actually monitored, so the org drifted into endpoint sprawl without ever making the deliberate switch the analysis intended as a safety valve.
- *Competitor/adversary:* low relevance for Option C specifically (a narrow, fixed set of REST aggregation endpoints has a small enumerable surface); this concern applies more to Option B, where an introspectable GraphQL schema is a larger target for query-cost/DoS probing absent depth/cost limiting.

**Clusters (structural weaknesses):**
- *Cluster 1 — Aggregation-endpoint design/ownership gap* (bears on C1, C4, C5's second-order extension). Triage: costly but survivable. Tripwire: a new mobile screen requires a backend code change and ships later than the client work, observed twice in a quarter — visible to mobile and backend leads via sprint retros. Disposition: **plan change** — require mobile+backend co-design review for any new aggregation endpoint, and assign explicit long-term ownership of the aggregation layer before Option C ships.
- *Cluster 2 — Wrong-bottleneck risk* (bears on the Essence Statement's own success criterion 1, and C4). Triage: fatal if true, but testable before committing. Tripwire: pre-implementation measurement of screen load time split into network-round-trip time vs. payload-transfer time vs. client-render time for the 3 mobile apps' worst screens — visible to whoever owns the mobile performance metric. Disposition: **plan change** — insert this measurement step before implementation begins; this surfaces the previously-unmeasured assumption ("round trips are the dominant contributor…") as something to close before, not after, committing engineering time.
- *Cluster 3 — Server-side fan-out shift* (bears on C5's second-order extension, and the underlying GT-4 dynamic applied outside GraphQL). Triage: costly but survivable. Tripwire: p95 backend-service latency or error rate behind the new aggregation endpoint crosses its pre-change baseline by >20% within two weeks of rollout — visible via existing SRE dashboards. Disposition: **explicitly accepted risk with a named mitigation** — apply DataLoader-style batching/dedup discipline inside the REST aggregation handler and load-test against realistic mobile traffic before full rollout.
- *Cluster 4 — Unmonitored trigger condition* (bears on C5's stated Option-B trigger). Triage: costly but survivable. Tripwire: none observed automatically — this is precisely the failure mode. Disposition: **plan change** — make "how many distinct aggregation endpoints exist, and is the count still small/stable" a standing quarterly architecture-review item rather than a one-time note in this analysis.

**Falsification:** This conclusion is false if a follow-up measurement shows round trips are not actually the dominant contributor to the mobile screens' load time (Cluster 2), or if the number of distinct chatty mobile screens needing bespoke aggregation is already large or fast-growing today rather than small and stable (which would mean Option B should be the starting point, not the fallback).
