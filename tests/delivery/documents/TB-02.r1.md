# 3. Ground Truths

- **GT-1** Amdahl's Law: for a task with serial fraction (1−p), speedup from N parallel units is capped at S(N)=1/((1−p)+p/N); as N→∞, S(N)→1/(1−p) — a hard ceiling on speedup from added parallel/faster hardware. Source: Amdahl, G.M. (1967), reprinted IEEE SSCS News, Summer 2007, pp.19–20; read-at-source: quoted "Overhead alone would then place an upper limit on throughput of five to seven times the sequential processing rate, even if the housekeeping were done in a separate processor," and the editor's caption: "Amdahl speculated that most programs would require at least 25% of the computation to be sequential… The curves show that the more you depend on parallelism for performance, the slower the system is likely to be in the probable case, 65%."
- **GT-2** In Google's production test system, when a previously-stable test became flaky and was traced to a specific code change, the change was a genuine production bug only 1/6 of the time — the rest was test-side flakiness, not real regressions. Source: Google Testing Blog, "Where do our flaky tests come from?" (2017); read-at-source: quoted "when a stable test became flaky, and we could track it to a specific code change, the problem was a bug in production code 1/6th of the time." (Used only to establish that flakiness-driven false signal is a real, documented failure mode in large CI systems — not transferred as this org's rate; see Dead End 2.)
- **GT-3** In trunk-based-development practice, the elapsed time between a commit and its failure notification is treated as a first-order design variable because repair cost rises with that delay. Source: trunkbaseddevelopment.com, "Continuous Integration"; read-at-source: quoted "The elapsed time between the commit and the 'this commit broke the build' notification, is key," and "the cost to repair things in the case of a build breakage goes up when additional commits have been pushed to the branch."
- **GT-4** A CI pipeline is a dependency-ordered stage graph (e.g., checkout → install → build → test → package), and stages with data dependencies on prior stages cannot start before those stages complete — a logical/toolchain necessity, not a policy choice, that fixes a non-zero minimum sequential critical-path length regardless of available parallel hardware. Read-at-source: definitional/directly inspectable in any dependency-graph-based CI configuration (e.g., `needs:`/`depends_on:` stage graphs).
- **GT-5** Expected number of attempts to obtain one successful run, given independent per-attempt success probability (1−f), is 1/(1−f) (mean of the geometric distribution): f=10%→≈1.11 attempts, f=30%→≈1.43, f=50%→2.0. Read-at-source: re-derived directly (E[attempts] = Σk·(1−f)^(k−1)·f = 1/(1−f)).
- **GT-6** Total elapsed wall-clock time for a CI run decomposes into queue-wait time (until a runner is allocated) plus execution time (once running) plus any retry cycles; these are separable and addressed by different levers — execution time by per-unit speed/parallelism, queue-wait by concurrent capacity (count), retries by reliability fixes. Read-at-source: definitional decomposition (a basic queueing-theory identity).
- **GT-7?** This organization's actual per-stage timing composition — the split between serial critical-path time, parallel-execution time (and how much parallelism is already achieved within it), queue-wait time, and retry overhead — is unmeasured. Unverified: no telemetry was supplied in this analysis and none was located.
- **GT-8?** This organization's test flake/retry rate is unmeasured. Unverified: not supplied.
- **GT-9?** This organization's merge-queue/runner-contention design (whether CI runs serialize or queue behind concurrent merge attempts, and how that scales with team size) is unmeasured. Unverified: not supplied.
- **GT-10** The number of potential pairwise interaction effects between n independent changes integrated together grows combinatorially with n (~O(n²) potential interaction pairs), and the number of candidate commits to bisect when something breaks grows with the number of changes bundled into one merge. Read-at-source: direct combinatorial derivation.
- **GT-11** Compute/runner spend (buying faster or more machines) is typically a recurring operating cost that scales with fleet size and usage for the life of the arrangement, while pipeline re-architecture (sharding, caching, suite-splitting, flaky quarantine) is typically a one-time or front-loaded engineering cost that continues paying off without proportional recurring spend as the team grows. Read-at-source: typical cloud/CI vendor billing structure (usage/seat-based, recurring) versus engineering labor cost structure (one-time); a general and largely definitional characterization, not a specific empirical citation.

# 6. Conclusion

**Recommended approach:** Instrument the pipeline before committing spend to either hardware or a re-architecture project: break the 47 minutes into per-stage wall-clock timings, separate queue-wait time from execution time, measure the test retry/flake rate, and compute the achieved parallelism ratio (wall-clock time ÷ summed stage CPU-time) (chain C5). Assign a named owner and a fixed (~2-week) decision deadline once that data exists, and track merge frequency / diff size as the real success metric rather than CI duration alone (chain C5). Buying faster and/or more runners is not ruled out: it is the correct move once the data shows the parallel-execution slice dominates the 47 minutes, the suite is already close to maximally sharded, and queue-wait and flake/retry rates are low (chains C3, C4). It is the wrong lever, and the spend would chase a mathematically capped and merely partial gain while the underlying architecture and reliability issues persist, if the data instead shows the serial critical path, queue contention, or flakiness dominates (chain C3).

**Key insight:** "47 minutes" is not a single homogeneous quantity that faster hardware acts on uniformly — it decomposes into a serial critical path bounded by Amdahl's Law, a parallel-execution slice, queue-wait time, and retry/flake overhead, and only one of those four shrinks in proportion to hardware speed (chain C1, chain C3). Reasoning by convention treats duration as a single compute-demand number; reasoning from these ground truths shows it cannot be treated that way.

**Trade-offs acknowledged:** Diagnosing first costs a small amount of calendar time (likely days) before either fix begins, against leadership's implicit preference for an immediately purchasable fix (chain C4). Restructuring the pipeline, if the data points that way, carries its own execution risk — test sharding can introduce new flakiness if done carelessly — which is priced into its lower reversibility score rather than treated as a separate concern (chain C4). Batching itself is not a neutral baseline: every additional change bundled into a pending merge compounds both defect-interaction risk and bisection cost, so delaying a decision has a real, growing cost (chain C7).
