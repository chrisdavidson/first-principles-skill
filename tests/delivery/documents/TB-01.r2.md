## 1. Problem Essence

**Core problem:** Given a shared REST API serving 9 client applications (3 mobile) where mobile screens require 4-6 round trips to render, should the team replace REST with GraphQL — or does the actual cause of the round-trip symptom call for a narrower, lower-risk fix (an aggregation/BFF layer, compound REST endpoints, or transport-level parallelization) that does not require a full API-paradigm migration?

**Success criteria:**
1. The Conclusion section names the specific mechanism (aggregation layer, compound endpoint, BFF, or GraphQL) that closes the round-trip gap, tied to a derivation chain.
2. The Conclusion section states explicitly whether the recommendation applies to all 9 clients or is scoped to the 3 mobile clients with the stated complaint.
3. The Conclusion section names at least one concrete, falsifiable condition under which the recommendation would flip toward full GraphQL adoption.
4. The Conclusion section's confidence rating accounts for the facts the task explicitly flagged as unknown (team size, backend architecture, caching setup, call sequencing) rather than silently assuming them away.

- **GT-1** 9 client applications consume a shared REST API; 3 of the 9 are mobile apps — source: user-supplied problem statement; read-at-source: task context, paragraph 1

- **GT-4** A GraphQL server operates on a single URL/endpoint (typically `/graphql`); the spec requires POST support for queries/mutations and permits GET; reliance on POST breaks default URL-keyed HTTP/CDN caching unless persisted documents, automatic persisted queries, or trusted documents are used — source: graphql.org, "Serving over HTTP"; read-at-source: quoted passages on single-endpoint operation, HTTP method requirements, and caching-workaround recommendations
- **GT-5** Naive resolution of nested/related GraphQL fields can multiply backend calls far beyond what the client sees — DataLoader's own example: "at most 13 database requests" naively vs. "at most 4... possibly fewer if there are cache hits" with DataLoader batching — this is the resolver-level N+1 pattern — source: github.com/graphql/dataloader README; read-at-source: quoted passage on the naive vs. batched request counts
- **GT-6** GraphQL query depth and complexity are unbounded by default, which "may lead to a DoS"; OWASP recommends depth limiting, query-cost/complexity analysis, and timeouts as mitigations not natively provided by GraphQL — source: OWASP GraphQL Cheat Sheet; read-at-source: quoted passages on unbounded depth/amount and the three recommended mitigations
- **GT-7** HTTP/2's primary goals are "to reduce latency and head-of-line blocking, by enabling full request and response multiplexing," letting independent requests proceed concurrently over one connection rather than only sequentially as under HTTP/1.1 — source: MDN, "HTTP/2" glossary entry; read-at-source: quoted passage on multiplexing goals
- **GT-8** The Backends-For-Frontends (BFF) pattern exists because "mobile devices will want to make different calls, fewer calls, and will want to display different (and probably less) data than their desktop counterparts," implemented as "one backend per user experience" — source: Sam Newman, samnewman.io/patterns/architectural/bff; read-at-source: quoted passages on the mobile motivation and the "one backend per experience" definition
- **GT-9** JSON:API (a REST convention) supports sparse fieldsets (`fields[TYPE]`) to avoid over-fetching and compound documents (responses that "include related resources along with the requested primary resources") to fetch related data in one response, without changing the underlying REST/HTTP transport — source: jsonapi.org specification; read-at-source: quoted passages on sparse fieldsets and compound documents
- **GT-10** For sequential, dependent HTTP requests (each waiting on the prior response), total latency accumulates additively (~N × (RTT + processing)); for independent requests issued concurrently over a multiplexed connection, latency is bounded by the slowest single call, not the sum — a definitional consequence of what "sequential/dependent" vs. "independent/parallel" mean, corroborated at the protocol level by GT-7 — source: definitional reasoning about request/response composition, corroborated by GT-7; read-at-source: GT-7's quoted passage

- **GT-12** GraphQL's query language lets a client specify nested field selections across relationship boundaries in a single request to the single endpoint described in GT-4 — this is the mechanism underlying its over/under-fetching pitch — source: graphql.org "Serving over HTTP" (single-endpoint framing) plus GraphQL's publicly specified nested-selection-set behavior; read-at-source: GT-4's quoted passage plus GraphQL's foundational, publicly documented query-shape semantics

## 4. Derivation Chains

### Conclusion C1: The round-trip symptom is a missing-aggregation-layer problem, not a REST-protocol ceiling

GT-1 (9 clients, 3 mobile) + GT-2 (4-6 round trips/mobile screen) + GT-8 (BFF pattern's mobile motivation) + GT-9 (JSON:API compound documents/sparse fieldsets)
→ REST APIs can serve nested/related composite data in a single response via compound documents and sparse fieldsets, so a fixed one-resource-per-endpoint shape is a design choice, not a protocol ceiling
→ the BFF pattern was created specifically to give mobile clients fewer, tailored calls while remaining on ordinary REST/HTTP, showing this exact symptom is routinely solved without swapping query languages *(theoretical-limit application: the network-level floor on client-perceived round trips is 1, regardless of API paradigm — GraphQL, REST, or gRPC all face the same client-server hop minimum, and GT-8/GT-9 demonstrate REST-based approaches already reaching that floor, so no paradigm has unclaimed headroom below what REST-based aggregation already achieves)*
→ the 4-6-round-trip symptom is best explained by this API's endpoints lacking a per-screen aggregation/shaping layer, not by an inherent ceiling in REST itself, and closing that gap does not require adopting a new query language

## 5. Abandoned Reasoning

### Dead End: Recommend full GraphQL migration on the stated complaint alone

**What was tried:** Initially treating the round-trip complaint as sufficient justification for a full GraphQL rewrite, mirroring the common industry narrative that GraphQL solves over/under-fetching by construction.

**Why abandoned:** The five-whys-style decomposition (C1) traced the symptom to a missing aggregation layer, and the inversion challenge (feeding C2, and the supporting pre-mortem below) showed GraphQL's fix is conditional on unverified backend-batching investment (GT-5) and new governance work (GT-6). The trade-off (C3) then scored this path far below both REST-based options even before fully weighting the unverified-capability risk.

**What it ruled out:** Re-litigating "GraphQL vs. REST" as a false binary the next time this same complaint recurs; the actual axis is "does this API have a per-screen aggregation layer," which several non-GraphQL mechanisms already answer.

### Dead End: Recommend gRPC as the fix

**What was tried:** Considered gRPC (protobuf, HTTP/2-native, strongly typed contracts) as an alternative wire protocol, since it is explicitly among the candidate alternatives.

**Why abandoned:** gRPC's core strengths — binary efficiency, streaming, strict contracts — address payload efficiency and service-to-service communication, not the specific "many separate resource calls per screen" aggregation problem. A gRPC client still makes one call per service method unless an aggregation/BFF layer sits in front of it, so gRPC does not solve the stated problem any more directly than plain REST does, while adding a new protocol, new tooling, and weaker native browser support relevant to the 6 non-mobile (likely web-facing) clients.

**What it ruled out:** Scoring gRPC as a fourth trade-off option; it would land near or below full GraphQL on cost/capability-fit without GraphQL's client-composability benefit, so it is dominated by options (b) and (c). Ruled out by C3's scope-fit and capability-fit criteria.

### Dead End: Treat "edge aggregation" as a distinct fourth trade-off option

**What was tried:** Considered scoring edge-compute aggregation (e.g., a CDN edge function doing the fan-out) as its own row in the trade-off matrix.

**Why abandoned:** Functionally, this is an implementation variant of the BFF pattern (GT-8) — *where* the aggregation logic runs (dedicated service vs. edge function) does not change the trade-off criteria's scores materially. Scoring it separately would double-count option (b)'s reasoning under a different deployment target.

**What it ruled out:** Needing a fourth column in the trade-off matrix that would not have changed any ranking; edge aggregation remains available as an implementation detail under option (b) if the team already runs edge infrastructure.

## 6. Conclusion

**Recommended approach:** Do not replace REST with GraphQL across all 9 clients on the evidence given. Instead, fix the missing aggregation layer directly: first add compound/batch REST endpoints and sparse fieldsets to the existing API and ensure mobile clients use HTTP/2 to parallelize any calls that remain, then escalate to a dedicated mobile BFF service for screens where compound endpoints prove insufficient. Scope this work to the 3 mobile clients with the stated complaint; the 6 non-mobile clients require no change (chain C5).

**Key insight:** GraphQL does not eliminate round trips — it relocates them, from the client-visible request layer to the server-side resolver layer — and it only pays off once the team has already done the aggregation-design work (plus resolver batching and query-cost governance) that a BFF or compound REST endpoint would have required anyway. The intuition that "GraphQL solves round trips" mistakes a client-facing request count for a total-latency guarantee (chain C2).

**Trade-offs acknowledged:** This recommendation gives up GraphQL's genuine long-term advantage for serving many heterogeneous, evolving client needs with a single flexible query surface — a real criterion in the trade-off, deliberately weighted low because the task asks to weigh against the stated pain, not hypothetical future needs (chain C4). It also accepts a risk of "aggregation-endpoint sprawl" if the pattern isn't generalized, mitigated by the named tripwires in the adversarial pass below (chain C4). Finally, the ranking between the two REST-based options (incremental fixes vs. a dedicated BFF) rests on qualitative, judgment-anchored trade-off scoring rather than measured pilot data (chain C3) — no chain — flagged assumption only for whether external/political pressure (A12) exists that would override this technical recommendation regardless of merit.

*Clusters:*

*Disposition:*
