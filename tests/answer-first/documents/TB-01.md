## 3. Ground Truths

- **GT-1** HTTP/2 (and by extension HTTP/3) allows a client and server to hold multiple concurrently open streams over a single connection, interleaved, so a client is not required to wait for one request/response to finish before sending the next — source: IETF RFC 7540, §5 "Streams and Multiplexing"; read-at-source: quoted "A single HTTP/2 connection can contain multiple concurrently open streams, with either endpoint interleaving frames from multiple streams."
- **GT-2** The Backend for Frontend (BFF) pattern — a dedicated server-side aggregation component per client experience, instead of one general-purpose API — is technology-agnostic: it can be implemented with REST, GraphQL, or any other transport, and its documented purpose is exactly the per-client-experience aggregation problem — source: Sam Newman, "Pattern: Backend For Frontend," samnewman.io/patterns/architectural/bff/; read-at-source: quoted "rather than have a general-purpose API backend, instead you have one backend per user experience... The BFF is tightly coupled to a specific user experience, and will typically be maintained by the same team as the user interface."
- **GT-3** GraphQL field resolvers execute independently with no built-in coordination or automatic batching; a query returning a list whose nested fields each require a separate backend fetch produces one fan-out call per item (the "N+1" problem) unless the server explicitly implements batching such as DataLoader — source: graphql-js.org, "Solving the N+1 Problem with DataLoader"; read-at-source: quoted "each field resolver runs independently. There's no built-in coordination between resolvers, and no automatic batching," with the worked example that fetching 10 posts with their authors triggers 11 total backend queries.
- **GT-4** A specification-conformant GraphQL server operates on a single URL/endpoint (conventionally `/graphql`); it must support POST for queries and mutations and may additionally support GET for queries only, and GET is what enables standard HTTP/CDN caching — complicated in practice because query strings can exceed URL-length limits, which is why persisted-query workarounds exist — source: graphql.org, "Serving over HTTP"; read-at-source: quoted "a GraphQL server operates on a single URL/endpoint, usually /graphql... Your GraphQL HTTP server must handle the HTTP POST method... and may also accept the GET method for query operations... because GraphQL documents strings may be quite long... the query parameters may exceed the limits that browsers and CDNs impose on URL lengths."
- **GT-5?** This organization has 9 distinct client applications consuming the API, of which 3 are mobile — unverified: stated by the requesting user as problem context; no client registry, API-gateway consumer log, or other document was cited or available to this analysis to confirm the count or the mobile/non-mobile split.
- **GT-6?** Mobile screens currently require 4-6 HTTP round trips to render, per the stated complaint — unverified: no telemetry, trace, or instrumentation data was cited; in particular this analysis has no evidence on (a) whether those 4-6 requests are sequential/dependent or already concurrent, or (b) how much of perceived screen-load time is attributable to round-trip count versus per-request server processing versus client-side rendering. This is the single most consequential unverified input in the analysis (see chains C2, C3 and the Conclusion).

## 5. Abandoned Reasoning

### Dead End: Generic multi-call HTTP batch endpoint as the fix

**What was tried:** Considered replacing the sequential per-resource calls with a `/batch` endpoint that accepts an array of sub-requests and returns an array of sub-responses in one HTTP round trip, as a lighter-weight alternative to a full BFF.

**Why abandoned:** This only reduces the transport/connection count; it performs no server-side data composition, so a client must still sequence any dependent sub-requests within the batch and glue results together itself, and it does not reduce backend call volume — still N backend calls, just multiplexed over one HTTP hop. This is contradicted by chain C1's finding that the real fix is server-side aggregation, and is recorded as Discard at A-10.

**What it ruled out:** Treating a transport-level batch endpoint as a standalone architectural fix. It may still be a useful short-term stopgap for pure connection-count issues, but it is not a substitute for aggregation and should not be proposed as the durable answer to the mobile complaint.

### Dead End: Adopt GraphQL because it is the modern/industry-standard approach

**What was tried:** Entertained the reasoning that, since many well-known companies use GraphQL for client-facing APIs, this org should adopt it too.

**Why abandoned:** This is reasoning by analogy, which the methodology bans as direct evidence. No verified ground truth ties industry popularity to this org's specific 9-client, 3-mobile cost/benefit profile. Recorded as Discard at A-11, and superseded by the dominance finding in chain C8.

**What it ruled out:** Using popularity or industry trend as justification anywhere in this analysis. Every claim here about GraphQL's merits or costs is grounded in GT-2/GT-3/GT-4 or the trade-off matrix, never in "others do it."

### Dead End: Adopt Apollo Federation / formal schema governance up front

**What was tried:** Considered specifying a federated-schema-ownership model as part of the recommendation, anticipating a future cross-team schema-coordination problem before it occurs.

**Why abandoned:** This solves a scale/governance problem that presupposes a GraphQL schema already exists. Since the recommendation (chain C8) is not to adopt GraphQL now, prescribing federation tooling is a premature optimization for a technology not being adopted. Recorded as Discard at A-12.

**What it ruled out:** Over-engineering the recommendation with GraphQL-specific governance machinery. The equivalent governance concern for the BFF option actually being recommended is instead handled directly as pre-mortem Cluster A (federated BFF ownership) in the adversarial pass record.

### Dead End: Full or partial GraphQL migration justified as future-proofing for the other 6 clients

**What was tried:** Considered recommending full or partial GraphQL migration on the grounds that it avoids paying a second migration cost later if the other 6 clients eventually need similar aggregation.

**Why abandoned:** This rests on GT-5?/A-9, an unverified assumption that those 6 clients will need it, and chain C8 shows the REST-BFF option weakly dominates REST-redesign and dramatically outperforms full GraphQL under every criterion given currently available evidence. Paying up front for a hypothetical future need that may never materialize — when the incremental extension cost later is mitigated by a reusable composition-layer requirement and a named tripwire (chain C8's third-order step) — is a dominated strategy under present evidence.

**What it ruled out:** Treating "avoid paying twice" as sufficient justification for full or partial GraphQL now. This remains the strongest live rival to the headline recommendation and is named explicitly as such in the adversarial pass record's Rival section below — it is not fully closed, only currently outweighed by the evidence in hand.

## 6. Conclusion

**Recommended approach:** Build a dedicated, mobile-scoped Backend-for-Frontend (BFF) / aggregation layer on top of the existing REST API, kept on REST/HTTP, to compose each mobile screen's data server-side into as close to one round trip as possible; do not undertake a full or partial GraphQL migration now, and leave the 6 non-mobile clients on the current REST API untouched (chain C8). Sequence the work so that measuring the actual cause of the round trips — sequential/dependent versus already-parallel execution — happens before any BFF code is written (chain C2).

**Key insight:** The mobile round-trip complaint is fundamentally a server-side data-aggregation problem, not a REST-vs-GraphQL problem — GraphQL's single-query round-trip reduction is achieved through the same mechanism (server-side composition across multiple backend resources) that a REST-based BFF already provides, so the technology choice affects cost, risk, and caching/observability compatibility far more than it affects whether the round-trip count can be reduced at all (chain C1). A second, equally non-obvious finding: GraphQL does not eliminate the fan-out that causes round trips, it relocates that fan-out from the client (visible as round trips) to the server (invisible resolver calls), which must itself be engineered against an N+1 explosion (chain C5).

**Trade-offs acknowledged:** This recommendation deliberately forgoes GraphQL's superior long-term, client-driven query flexibility for heterogeneous or rapidly-changing screen needs, accepting a less flexible, hand-maintained composite-endpoint model instead (chain C1); it also accepts the residual risk that if the other 6 non-mobile clients eventually need similar aggregation, some BFF design work may need extending later rather than being built once for all 9 clients up front (chain C4); and it accepts that the true magnitude of benefit is unverified and could be much smaller than estimated if the round trips already execute in parallel today (chains C2, C3).

**Evidence that would change this recommendation:**
- Instrumentation showing the round trips already execute concurrently over a multiplexed connection, with backend processing time as the dominant latency driver, would redirect the fix toward backend performance work instead of any API-shape change (chain C2).
- A survey showing the 6 non-mobile clients have an independent, comparably severe multi-round-trip problem would justify widening the aggregation approach to them too, though not necessarily via GraphQL (chain C4).
- Evidence that mobile's per-screen data needs are highly heterogeneous and rapidly evolving, such that composite REST endpoints would proliferate uncontrollably, would tip the long-term-flexibility criterion enough to favor GraphQL behind the BFF (chain C1).
- An audit showing current CDN/reverse-proxy caching absorbs a large share of the existing REST API's load would raise the cost of any GraphQL option further, reinforcing this recommendation (chain C6).
- A demonstrated team pilot or existing staff expertise in GraphQL/DataLoader-style batching would reduce the leverage-of-existing-skill cost penalty against GraphQL options in the trade-off (chain C5).
