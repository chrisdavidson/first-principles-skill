3. Produces a decision recommendation with an explicit, checkable confidence level — not a flat yes/no.

# 3. Ground Truths

`?`-marked: GT-10 (1 of 10).

- **GT-1** (read-at-source: user's problem statement, this conversation) — The CI pipeline takes 47 minutes end-to-end.
- **GT-2** (read-at-source: user's problem statement) — Developers batch multiple commits/PRs into single merges specifically to reduce how often they trigger the pipeline.
- **GT-3** (read-at-source: user's problem statement) — Leadership's proposed fix is buying faster/more CI runner hardware.
- **GT-4** (definitional — mathematical identity, no external source needed) — Amdahl's Law: wall-clock speedup from parallelizing or accelerating the parallel portion of a workload is bounded above by 1/s, where s is the serial (non-parallelizable, non-accelerable) fraction; speeding up only the parallel portion cannot push wall-clock time below s × total duration.
- **GT-5** (definitional, via reduce-to-primitives) — Network/I/O wait time is a function of data volume, bandwidth, and latency and contains no CPU-speed term; it does not shrink with faster CPUs.
- **GT-6** (definitional, via reduce-to-primitives) — Wall-clock time added by flaky-test retries = (expected retry count) × (test duration); expected retry count is driven by flake rate, not runner CPU speed.
- **GT-7** (definitional, via reduce-to-primitives / queueing theory) — In a shared runner pool, pre-execution wait time is a function of arrival rate versus available concurrent slots, not the speed of an individual runner once running; it is relieved by added concurrent capacity, not necessarily by faster per-unit hardware.
- **GT-8** (definitional — fixed-cost amortization identity) — If each pipeline trigger imposes a fixed cost C regardless of diff size, batching N changes into one trigger reduces amortized cost-per-change from C to C/N — a monotonic incentive to batch whenever C is perceived as high relative to the value of frequent independent feedback.
- **GT-9** (read-at-source: user's problem statement, by absence) — No per-step timing breakdown, CPU/network/disk utilization data, flaky-retry rate, or runner-queue wait-time data has been supplied for this specific pipeline.
- **GT-10?** (unverified — industry-pattern heuristic, not sourced to a measured study or to this pipeline) — CI pipelines of comparable end-to-end length commonly have a serial/non-accelerable fraction in the rough range of 15-40% of total wall-clock time. *Phase 3 failure record: no citable source was located for this range; it is used only as an illustrative planning heuristic in C3/C4, both of which are explicitly disclaimed as non-load-bearing for the headline recommendation.*

# 6. Conclusion

**Recommended approach:** Do not buy faster/more CI runners as the first move. Run a short, time-boxed (days, not weeks), cheaply-instrumented diagnostic pass — per-step timing breakdown, CPU/network/disk utilization during runs, flaky-test retry rate, and runner-queue wait time — to identify which of the six candidate categories (compute, parallelization/architecture, test-suite composition, I/O/caching, flakiness/retries, queueing/contention) actually dominates the 47 minutes, then apply whichever targeted fix the data indicates. Buy hardware only if the diagnosis specifically confirms compute-bound dominance with limited remaining parallelization headroom, or confirms queueing/contention dominance — and in the latter case, buy *more concurrent capacity*, which is a different purchase than "faster" runners (chains C2, C3, C4, C6).

**Key insight:** The batching workaround is not a discipline problem; it is a rational response to a fixed per-trigger cost being amortized across N changes (chain C1). That means only a fix that meaningfully reduces the fixed-cost character of the pipeline — a large proportional cut, or a structurally different fast-feedback path for typical small diffs — will actually change developer behavior. A marginal duration reduction (the realistic range for "faster CPUs" alone, per the illustrative and explicitly non-load-bearing C3/C4 brackets) is unlikely to cross that threshold.

**Trade-offs acknowledged:** Diagnosing first costs a few days of engineering time and defers the visible "we did something" signal to leadership; buying hardware blind is faster to announce but risks spending money without changing behavior, burning credibility on the decision, and entrenching the real bottleneck via sunk-cost-influenced reluctance to revisit the bet (chain C5). The trade-off analysis (chain C6) shows diagnose-first dominates buy-hardware-only, do-nothing, and diagnose-then-generic-fix by a robust margin (74 vs. 65 vs. 53 vs. 41; no single-weight change flips the ranking), though the specific weights/scores are illustrative and should be re-run with the organization's real cost figures (A-14) before committing budget.

**Confidence: MEDIUM.** Rests on chains C1 (HIGH), C2 (HIGH), C5 (MEDIUM), C6 (MEDIUM) — lowest cited MEDIUM, so Inputs ceiling is MEDIUM. The structural recommendation (diagnose before buying) does not depend on the specific Amdahl-based percentage brackets in C3/C4 (both LOW, both explicitly disclaimed as illustrative, non-load-bearing context) — it holds even in the world where those brackets are wrong. What would raise this to HIGH: replacing GT-10?'s industry heuristic and A-12/A-14's illustrative figures with this specific pipeline's actual telemetry and this organization's real cost numbers — which is precisely what the recommended diagnostic phase would produce.
