# 4. Derivation Chains

**Theoretical-limit note (feeds the efficacy anchors below):** the governing constraint on round-trip count is that data resolution can happen client-side (one HTTP exchange per dependency step) or server-side (arbitrary dependency depth resolved behind one HTTP exchange). The **ideal floor is 1 round trip**, reachable by any approach that moves aggregation server-side (GT-1, GT-3) — regardless of whether that server-side layer is written in GraphQL, plain REST/JSON, or anything else. A client-side/network-only fix (HTTP/2 multiplexing, GT-2) cannot reach this floor when calls are sequentially dependent, because multiplexing only removes contention among *concurrent* requests, not the need for a second request whose parameters come from the first. This is why the efficacy anchors below separate "server-side aggregation" options from "network-only" options.

A differently-weighted analysis, if long-term flexibility were judged far more important than weighted here, would flip the recommendation toward D.

**What it ruled out:** treating "best raw technical capability" as sufficient justification on its own, independent of cost, caching, and operational-risk criteria the organization also cares about — and it flags D as the correct re-evaluation target (Cluster 4's tripwire) if the org's client-type breadth grows materially.

### Dead End 2: Treat "REST cannot aggregate data in one round trip" as a ground truth

**What was tried:** initially considered folding this into the Ground Truths list rather than the Assumptions Table.

**Why abandoned:** GT-3 (the BFF pattern) is a direct existence proof that REST/HTTP-style APIs can return aggregated, nested payloads in one round trip — the limitation is a design/granularity choice in the current API, not a property of REST itself. Discarded as assumption A-3.

**What it ruled out:** any downstream chain treating "must leave REST" as a forced conclusion of the round-trip complaint.

### Dead End 3: Score the full-migration option (B) in the trade-off matrix instead of knocking it out

**What was tried:** considered scoring B on all seven criteria to let its numbers speak for themselves.

**Why abandoned:** scoring it would let a strong secondary-criterion showing (e.g., long-term flexibility, if B were scored like D) out-vote the hard non-disruption constraint (must-have ii) — exactly the failure mode the trade-off procedure's knockout step exists to prevent.

**What it ruled out:** any weighted-total argument for full migration; the knockout is applied structurally, before any score can compensate for it.

# 6. Conclusion

**Recommended approach:** Do not replace REST with GraphQL. Treat this as a mobile-scoped aggregation-layer gap: ship a single purpose-built composite REST endpoint for the worst-offending mobile screen first, formalize it into a mobile-owned Backend-for-Frontend service once more than 2-3 screens need the same treatment, keep ownership with (or tightly co-owned by) the mobile teams rather than the central API team (chain C4), and — before committing further budget — instrument the mobile app's network calls to determine whether the 4-6 round trips are independent or sequentially dependent, since that single fact determines how much of the problem a near-zero-cost HTTP/2-plus-parallel-fetch approach could already solve (chain C5). The 6 non-mobile REST consumers require no changes under this plan (chain C2).

**Key insight:** "REST vs GraphQL" is the wrong question. The real gap is that 3 of 9 clients need server-side data aggregation the other 6 don't need — and once reframed that way, GraphQL is not even the winning technology for that aggregation layer: a plain REST-shaped BFF outscores a mobile-scoped GraphQL gateway (112 vs. 94) chiefly because GraphQL forfeits REST's built-in HTTP/CDN cache identity and introduces a new class of N+1 performance risk that a REST aggregation endpoint does not (chains C1, C3).

**Trade-offs acknowledged:** This plan trades away the long-term flexibility a GraphQL gateway would offer — if the organization later needs many more client types or ad hoc query shapes, today's bespoke REST composite endpoints may accumulate duplication (chain C4), and the team may eventually revisit a GraphQL or gateway layer (Dead End 1). It also defers a firm build decision until the round-trip dependency structure is measured (chain C5); shipping C3 without waiting for that measurement is a live, unsettled alternative if delivery speed matters more than the modest risk of over-building — no chain — flagged assumption only. It assumes the BFF's ownership will actually sit with (or be shared with) the mobile teams; if organizational structure prevents that, chain C4's benefit does not materialize (chain C4).
