## The four failure chains

| Chain | Failure | Root cause |
|---|---|---|
| **A — Undetected revenue leak** | A silently failing payment method/currency/SCA path hits all customers; detected hours late → unrecoverable revenue loss | No early-warning cohort + no per-method alerting |

The key insight: these aren't four separate risks — they all route through **one decision**. The big-bang design deletes every early-warning cohort and every cheap escape hatch. None of the chains require the rewrite to be *bad*, only *imperfect* — which all software is.

## Five recommended changes (each kills a chain at its root)

1. **Add a staged rollout (canary):** 1% → 10% → 50% → 100%, with shadow/parallel traffic first. Highest-leverage change.
2. **Move off Friday** to Tue/Wed morning, so failures surface with full staffing + vendor support.
3. **Rehearse the rollback** before cutover, state-aware. If it isn't clean and fast, the launch isn't ready.
4. **Pre-wire per-payment-method success-rate alerting** with an auto-rollback threshold.
5. **Define the in-flight-state cutover plan:** dual-write/drain pending captures, preserve idempotency keys + webhook ordering, run reconciliation.

**The one thing to verify before any sign-off:** *Does a rehearsed, state-aware rollback path actually exist?* That single unknown is the difference between "risky but recoverable" and "betting the EU payments line on a Friday."
