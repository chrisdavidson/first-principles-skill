## Load-bearing finding: cost arithmetic at 500 writes/sec

500 writes/sec = 1.314 billion writes/month, with transactional semantics (orders + inventory + payments applied atomically):

- **PostgreSQL** (Multi-AZ, 200GB): $259.88 compute + $46 storage = **$305.88/mo**. Transactional writes are native — no per-write surcharge.
- **MongoDB Atlas** M30: $389 base + ~30% transfer/backup ≈ **~$506/mo** (uplift estimated, not verified).
- **DynamoDB on-demand, transactional** (2× WRU): 1,314M × 2 × $1.25/M = **$3,285/mo — over budget**, before any GSI. One GSI doubles it to $6,570/mo. Provisioned mode ($475–$949/mo) fits on cost but reintroduces capacity-planning/throttling risk and doesn't fix the relational mismatch.

## Two challenged assumptions

1. **"Transactional" doesn't mandate one engine** — all three have a transaction primitive; the differentiator is how *naturally* each supports it. Native multi-row ACID (PG) beats multi-document txns (Mongo) beats TransactWriteItems (2× cost + 100-item limit).
2. **500 w/s isn't the binding constraint** — it's modest; all three clear it easily. The real deciders are ACID/relational fit and cost.

## Why not the others

- **MongoDB** (viable fallback): fits budget, scales well, but weaker multi-document transaction story for tightly-coupled order/inventory/payment integrity; core entities are relational, not document-shaped.
- **DynamoDB** (rejected): breaches budget on transactional on-demand writes; key-value model fights relational queries/reporting; proprietary API imposes the highest future migration cost.

## Confidence: HIGH on the ranking

**Weakest link — read load is unspecified.** E-commerce reads usually dwarf writes; this is the one open input affecting *sizing*. But it would *strengthen* Postgres (mature read-replica + caching ecosystem), not overturn the choice.
