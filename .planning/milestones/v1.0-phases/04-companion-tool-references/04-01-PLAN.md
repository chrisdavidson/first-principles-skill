    1. H1 title `# 5-Whys` as the very first line (SC-4: no YAML frontmatter — file's first character is `#`).
    2. A 1-2 sentence blockquote scope note immediately under the H1 (per 04-PATTERNS Opening Pattern): what the tool does plus the trigger that brought the reader here. Do NOT use the bold `**Scope:**` label (that phrasing belongs to validation-rubric.md). This is a brief orientation, NOT the When-to-use section.
    3. `## When to reach for this` — the use case (a symptom that keeps recurring, surface fix does not prevent recurrence, the problem has a traceable causal chain) plus a contrast clause stating when NOT to use it (multiple interacting system failures suspected — use a fishbone/Ishikawa approach instead).
    4. `## Procedure` — imperative mood, follow the canonical Five-Whys procedure pattern in 04-RESEARCH.md lines ~465-486. Use bold-step labels (`**State the symptom.**`, etc.), not a plain numbered list. The procedure MUST: model causes as a branching tree (instruct "ask what else caused this" at each level before going deeper, one branch completed before the next); state the stop criterion as the Corrective Action Test — stop drilling a branch when BOTH a specific implementable corrective action can be stated AND that action is within practical control; instruct that a branch reaching a cause with no actionable corrective is recorded as a real finding, not discarded; require each causal link be validated against observable evidence, flagging inference as assumed. The word "five" must NOT appear as a stop rule (SC-1: test-based, not count-based) — if iteration count is mentioned at all, frame it only as a typical range.
    5. `## Example` — a mini-example in the everyday/non-technical domain (D-04). Use a recurring household problem — RESEARCH.md suggests "bread keeps going stale before it's finished"; adopt that or an equivalent recurring everyday symptom. Must NOT use any of the four Phase 5 worked-example domains (software / product / personal / science). Show it as a nested bullet list (symptom → first-level causes → second-level causes per branch). Annotate which branch triggers the stop criterion and what the corrective action is.
    6. `## Failure modes` — surface the failure modes for 5-Whys (Claude's discretion which to include; draw from 04-RESEARCH §Failure Modes and Pitfalls — e.g. count-driven stopping, single-thread tunnel vision skipping the branch question, "probably because X" links with no evidence, confirmation bias toward a suspected cause).
    7. `## Handoff` — 1-3 sentences only (Pitfall 5: more than 3-4 lines is a warning sign). Written as a pointer back to the methodology, not a hard dependency (D-08): name what the tool's output is (the identified root cause(s)), name the phase it feeds — Phase 2 (Challenge Assumptions) when drilling on a why-is-this-true question, or Phase 4 (Reason Upward) when drilling on a causal claim mid-derivation — and name the artifact it contributes to (a row in the Classified Assumptions Table, or a step in a Derivation Chain). Do NOT re-explain what Phase 2 or Phase 4 does.

    Place a `---` horizontal rule between every `##` section (04-PATTERNS Section Dividers). Use `##` for all named components; no H3. Keep the whole file roughly under 100 lines (D-06) — every sentence carries weight, no preamble explaining what first-principles thinking is, no "feel free to adapt." Do NOT paste methodology content into the file. The file must be runnable standalone (D-07): a reader with no prior knowledge can execute the procedure from this file alone.
