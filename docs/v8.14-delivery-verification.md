## 1. What this record establishes

This record establishes, from git-tracked dated evidence, whether the `8.14.0` version stamp
actually reaches an installed session through two distinct delivery mechanisms — the fresh-install
path and the existing-install update path. Per D-07 these are two different mechanisms with two
possibly different answers, and both are published side by side here, never collapsed into one
headline. Both answers are published whichever way each falls: "the stamp reached installs fine
and nothing was ever undeliverable" is itself a passing result for DELIV-01, and simultaneously
the exact condition that fires this record's own STOP branch in §2 below — the admissibility
anchor for Phases 189-191 depends on finding a real hole, not on this milestone's preference for
one.

## 6. Limitations

- **The update arm's marketplace source is a local clone, not the GitHub remote.** This deviates
  from D-02: the local-clone construction is the only one that exercises version-gating end to
  end, because a `directory`-source marketplace can be checked out at an old commit and then
  advanced in place, which a GitHub remote source cannot be made to do inside this run. The
  fresh-install arm's remote-source result therefore does not transfer to the update arm's source
  type — they are two different mechanisms, not one mechanism observed twice.
- **The isolation is split.** The install and update mechanics for both arms ran inside disposable
  `CLAUDE_CONFIG_DIR` scratch directories under `/tmp`. Both live invocations, by contrast, ran
  under the *default* authenticated `~/.claude` config with `--plugin-dir` pointed at the
  scratch-installed cache path, because a scratch config dir carries no credentials and cannot run
  a live session on its own. Credentials never entered a scratch directory; only the dispatch step
  borrowed the default config.
- **The live limb is a single non-deterministic observation.** One invocation ran per arm. Agent
  and skill dispatch in this project is documented elsewhere as varying run to run, so each arm's
  "Launcher runs" cell is a dated observation of one run, not a repeatable measurement, and a
  re-run may differ.
- **The offline limbs are reproducible; the live limb is not.** Re-running either arm from a fresh
  `mktemp -d` reproduces the registered marketplace name, the installed version label, the
  recorded `gitCommitSha`, and the byte-diff verdict identically, because those depend only on the
  source tree and the CLI's install mechanics — not on model-dispatch behaviour.
- **n = 1 per path, one machine, one CLI version.** Both arms ran once each, on one machine,
  against `claude --version` `2.1.220 (Claude Code)`. No repeat-and-aggregate protocol was run
  here.
- **The update arm was exercised with a version bump present.** This run establishes that the
  update path delivers when the version stamp advances — pre-update `8.6.0` to post-update
  `8.14.0`, with a matching `gitCommitSha` change. It does not establish what happens when the
  plugin's content changes but the version stamp does not advance, which is the exact shape of
  condition DELIV-03's rule exists to prevent. That question remains open.
- **The `8.6.0` specimen's own recorded provenance pointer does not resolve.**
  `~/.claude/plugins/installed_plugins.json`'s live entry records `gitCommitSha`
  `220784c74ae58243a7bf8f742e13fa323c90fe41`; that SHA no longer resolves in this repository after
  the 2026-07-28 history purge (`git cat-file -t` on it fails). The specimen's installed record is
  itself carrying a dangling provenance pointer, unrelated to and unaffected by either arm run
  above.
