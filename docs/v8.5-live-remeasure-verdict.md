## 2. Fishbone marker-perturbation check (D-05)

S-P03 is the row with room to fall — its v7.11 floor is 4/5 while the other four rows sit at
or below 2/5 already — so it carries most of this verdict's signal, and most of its risk of
misreading. The frozen marker count of 7 is read from output *text*; Phase 154's split moved
fishbone's `Example` / `Failure modes` / `Handoff` sections into
`shared/references/fishbone-detail.md`, which the model may never read. If markers stop
appearing because their prompting content moved, K/N falls for a reason that is **not** a
routing regression. A count alone cannot tell the two apart — only a fired-marker *set* can.
`/tmp/fishbone-fired-set-v85.py` (throwaway, not committed, not a battery row or gate) derived
that set for every S-P03 run on both generations by importing
`scripts/_battery_core.py`'s own `_TECHNIQUE_CATEGORIES["fishbone"]` (asserted at exactly 7
patterns, aborting non-zero on drift) and checking each pattern against the assistant-text
excerpt directly, rather than reimplementing the detector's regex list by hand. Its fired-set
size agreed with the production `_technique_hits()` count on the cross-check run, confirming
the per-index matching reproduces the real detector.

### Artifact-versus-regression reading

The interpretive rule stated in D-05: a marker that dropped and whose prompting content moved
into `shared/references/fishbone-detail.md` under Phase 154's split is a **measurement
artifact** — the technique still ran, the output simply no longer echoes that phrase because
the phrase's source text is no longer default-loaded. A genuine routing miss loses the
structural headers too, not just prose-flavour markers.

Checking each of the four dropped/declined markers' source text against the split boundary
(`shared/references/fishbone.md`, always inlined, versus `shared/references/fishbone-detail.md`,
on-demand):

| Marker | Where its source text lives | Reading |
|---|---|---|
| `cause_category` | Core `fishbone.md` ONLY (section header "Cause categories") | **Not moved.** Its prompting content is still always-inlined; the split cannot explain its loss. |
| `sub_causes` | Core `fishbone.md` ONLY (Procedure step 4, "Identify sub-causes") | **Not moved.** Its prompting content is still always-inlined; the split cannot explain its loss. |
| `preset_6M_8P_4S` | Neither file — the regex `\b(6M|8P|4S)\s+(preset\|categor)` does not match any current sentence in `fishbone.md` or `fishbone-detail.md` (the Named-presets section uses table/heading formatting the pattern was never built to match) | **Not explained by the split.** This marker never depended on content placement; it fires only on a specific phrasing the model itself must generate. |
| `candidate_causes` | **Both** core `fishbone.md` (Procedure step 3, "generate candidate causes") and `fishbone-detail.md` (Failure modes, "Every entry on a fishbone is a candidate cause") | **Partially consistent with the artifact hypothesis** — this is the one marker whose source text was duplicated into the detail file, and it declined (4/5 → 1/5) rather than being lost outright. |

**Reading, stated plainly: the evidence does not support the measurement-artifact hypothesis
as the primary explanation.** Three of the four affected markers — `cause_category`,
`sub_causes`, and `preset_6M_8P_4S` — have source text that is either still entirely in the
always-inlined core file or not traceable to either file's text at all; none of these three
had their prompting content relocated to the on-demand appendix, so the split's on-demand load
mechanism cannot mechanically explain why they stopped firing. Only `candidate_causes` fits
the artifact pattern (its text is duplicated in both files), and even there the marker did not
vanish — it declined from 4/5 to 1/5, still firing on one run. At the same time, this is not a
clean "genuine routing miss" either in the harsh sense D-05 describes: the **structural
anchor** `fishbone_or_ishikawa` — the technique's own name — fired 5/5 on every single run in
both generations, and `people_process_tech`, a structural category-preset marker, held steady
at 2/5 in both. The technique is still being correctly identified as fishbone on every run;
what narrowed is the *depth* of procedural vocabulary the model echoes back (naming specific
sub-steps like "sub-causes" or the preset names), not whether it recognises and runs the
fishbone technique at all. The K/N drop from 4/5 to 3/5 is mechanically explained by two runs
(3 and 4) losing one distinct marker each and crossing below `MIN_HEADER_HITS=2` — a narrow,
single-marker margin in both cases, not a wholesale structural collapse. **Net reading:** the
decline is best characterised as a genuine, if modest, drop in procedural-vocabulary echo
depth across runs — not a measurement artifact traceable to the split's on-demand load
mechanism, since the vocabulary that stopped firing remains in the always-inlined core file.
