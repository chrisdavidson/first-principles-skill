## 1. Scope and Standing

This is the D-01 successor governing record for Phase 40, naming
[`v8.7-constraint-teardown.md`](v8.7-constraint-teardown.md) as the record it succeeds and
following that record's §4 procedure step by step, once per retired or relaxed item.

This is a **subtraction record against a default-frozen baseline**. Anything not explicitly
named in §2 below stays frozen and gating by default — silence never means permission. A future
milestone finding this document silent on a constraint it wants to touch must treat that silence
as "still frozen," the same rule `v8.7-constraint-teardown.md` §1 states for itself.

**D-02 — this record is separate from the source-literal pinning phase's relaxation record.**
That record's parent is [`v8.5-byte-freeze-relaxation.md`](v8.5-byte-freeze-relaxation.md) §4, and
its procedure is distinct from this one. The two are not merged: this record follows
`v8.7-constraint-teardown.md`'s "What Is Retired" shape, the other follows
`v8.5-byte-freeze-relaxation.md`'s "What Is Relaxed" shape, and each names its own predecessor.

**D-04 — both predecessor records stay byte-intact.** No in-place edit is made to
`docs/v8.7-constraint-teardown.md` or `docs/v8.5-byte-freeze-relaxation.md`, including to the
teardown record's own §5 battery-composition text. Every correction to either record's substance
is stated here, in this successor record, instead.

**REACH-or-LEVEL, answered in writing (standing instruction 3).** A retirement is neither. It adds
no guard and widens no existing guard's reach over more product surface — it removes a check and,
where a replacement is warranted, moves an assertion of a real property onto an *existing* gate
(REG-GUARD) rather than building a new one. `docs/PROCESS.md` §1.1's own test — REACH points an
existing product-guard at more product surface; LEVEL adds a guard whose subject is another
guard's own correctness — does not classify a subtraction at all; nothing here is scored as either.

**No ordering constraint against the source-literal pinning work.** The six scripts named below
hold none of the literals the source-literal pinning milestone's pre-registered census counts
(checked at Phase 40's opening against that milestone's own pivot record), so this phase carries no
sequencing dependency on that work and may land before, after, or interleaved with it.

**D-09 — provenance, not evidence of record.** The 2026-09-13 filing readings (at commit `2c3f0c1`)
are cited below only as where a finding originated. Every reading quoted as evidence in §2 was
re-measured at this phase's own base commit, `dc84840`, on 2026-09-15.

**Decision and rationale.** **Retire VAL-05 outright — option (b). This overrules the research's
recommendation of option (a) (replace with a documented 1,536-character per-skill limit).**
Rationale, from the evidence above: the only skill ceiling the platform documents is the
1,536-character truncation of the combined `description` and `when_to_use` text "in the skill
listing" — a display truncation, not a validation failure — and the invocation table states that a
`disable-model-invocation: true` skill's description is "Not in context" at all. All 14 shipped
skills carry that setting (§2.2). A 1,536-character assertion would therefore guard the same
absent listing VAL-05 is being retired for; §2.2's `disable-model-invocation` pin is precisely what
keeps that listing irrelevant, so adding a second gate for a listing that never renders would not
close a real gap. The 15,000-token sub-agent figure is a startup warning over *combined*
descriptions across an entire subagent roster, not a per-skill ceiling — a character-count proxy
for it would invent a new ceiling with no stated basis, the exact defect class being retired. The
agent's own `description` is already bounded at 1,024 characters by GATE-01
(`scripts/check-agent.py`, `_MAX_DESCRIPTION_LEN = 1024`) — that check is untouched by this
retirement. The skill-side 1,024-character figure named in `CLAUDE.md`'s Key invariants list has no
source on the platform's skills page and is not what VAL-01 or GATE-01 enforce (M3(b) above shows
`claude plugin validate` passes a 1,100-character skill description untouched) — it stays a
documented repo convention with no gate behind it. If a later mutation shows VAL-01 or GATE-01
actually going red on an over-length skill description, name that gate as the owner instead of
"convention" — the decision to retire VAL-05 is unaffected either way.
