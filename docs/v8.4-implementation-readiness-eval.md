## Methodology

decision" (following v8.1 external-review triage, v8.2's re-investigation of v8.1's 19
not-approved items, and v8.3's technique/context-optimization evaluation). Where v8.3 identified
and ranked candidate optimizations as findings, this document renders the fresh go/no-go verdict
plus costed implementation-readiness plan that v8.3 explicitly deferred to a future milestone —
for the two v8.3-surfaced candidates named in this milestone's scope. The four governing
decisions, carried in intent from
[`150-CONTEXT.md`](../.planning/phases/150-implementation-readiness-evaluation/150-CONTEXT.md):

- **D-01 — Reuse v8.3's D-04 4-factor composite with factor 1 relabeled to "value."** The
  consolidated prioritized disposition (§5) reuses v8.3's [section 6](v8.3-technique-context-optimization-eval.md)
  D-04 4-factor composite with factor 1 relabeled from "context-savings" to "value" (scored 1-3).
  The remaining three factors — goal-fidelity-risk, byte-freeze-cost, implementation-effort — and
  the formula `value x (4 - risk) x (4 - byte-freeze) x (4 - effort)` carry over **byte-identical**
  from v8.3 §6; only the label and the scale definition of factor 1 change. Rationale: a
  savings-only axis provably cannot score a line-*adding* candidate — v8.3 itself excluded its own
  §4 #6 item on exactly that ground ("it would *add* lines, not save them — and is therefore not
  scoreable on the same savings-composite axis"). Relabeling makes line-savings one *kind* of
  value, so both a line-saving candidate (extraction) and a line-adding candidate (the banner) land
  on a single defensible ranking scale.
- **D-02 — The value scale is a superset that preserves v8.3's arithmetic.** v8.3's line-count
  thresholds (under ~50 lines is 1; ~50-150 is 2; 150+ lines or a headline lever is 3) remain the
  scoring rule for a savings-type item; non-savings value is anchored alongside on the same 1-3
  scale (3 = unblocks a stated top-priority ask / headline-level value). The extraction's savings-3
  therefore maps to value-3 **by construction**, and its composite must reproduce **24 exactly**
  (§5 shows this arithmetic explicitly, not merely asserts it — v8.3's published rank-4 score is
  reproduced under the relabel, never silently moved). Rationale: v8.3 is SHIPPED and its rank-4
  composite of 24 is a published number; a relabel that quietly moved it would put this document in
  contradiction with a shipped doc, which the project's no-contradiction convention forbids.
- **D-03 — Verdicts are independent of the composite; disagreement is flagged, not hidden.** The
  GROK04-01 (§1) and EXTRACT-01 (§3) GO/NO-GO verdicts are reached independently, purely on their
  own evidence — **never derived from the composite score**. The composite's only job is to *order*
  items within §5's consolidated disposition. If a verdict and the composite rank disagree (a
  NO-GO item outranking a GO item, or vice versa), §5 flags that disagreement as an explicit
  finding rather than silently listing items in composite order. Rationale: prevents a 1-3
  subjective scale from quietly deciding a build/defer binary — the false precision the project's
  honesty-not-score convention resists; a rank/verdict mismatch reads as an error to a future
  reader unless the document narrates it.
- **D-04 — Extraction's composite inputs are fixed from v8.3, plus an explicit sensitivity note.**
  The extraction's composite inputs are **consumed as fixed from v8.3** (value 3 / risk 2 /
  byte-freeze 2 / effort 2 = 24) — no re-derivation of v8.3's own analysis. §5 additionally carries
  an explicit sensitivity note covering two soft spots surfaced during scouting: (a) whether the
  `Handoff` section of each split reference file is procedural (core) or worked-detail (appendix) —
  if it stays in core, the four-file line saving drops from ~406 to ~285 against v8.3's claimed
  "400-600+", pressuring the value-3 score; and (b) no mechanism to load a `-detail.md` file
  currently exists (`{{PROCEDURE:slug}}` removal is free, but the on-demand deep-dive load surface

**(5) Text-vs-shapes cross-viewer risk.**

The tension is real and stated plainly: `svg-precision`'s own Spec design rules (`SKILL.md`, read
this session) warn *"Text varies by fonts/viewers. If you need pixel-identical results, treat text
as a risk and prefer shapes,"* while GROK-04's banner concept is explicitly typographic — a
project-name wordmark plus a motif evoking the 5-phase pipeline. Three postures are available:

- **Live `<text>` elements (as sketched in part (1)).** Smallest spec, smallest effort — a single
  `text` element per line of copy. Renders differently across viewers depending on installed fonts
  and each browser's fallback chain when the declared `fontFamily` ("Inter, system-ui,
  sans-serif") isn't available; GitHub's Markdown renderer displays the SVG through the visitor's
  own browser, so the wordmark's exact glyph shapes are not guaranteed identical across visitors —
  though it stays legible via the generic `sans-serif` fallback in every case.
- **Convert the wordmark to vector path outlines.** Deterministic, pixel-identical rendering across
  every viewer regardless of installed fonts. But the resulting spec is materially larger (dozens
  to hundreds of path points per word, versus one `text` element), the wordmark is no longer
  hand-editable as a string (renaming the project would require re-deriving the outlines from
  scratch), and — critically — `svg-precision`'s own documented pipeline (`build` / `validate` /
  `render` / `diff`) provides **no font-to-path conversion step**; a future implementer would need
  an external tool or manual glyph-tracing outside this skill's contract to produce it.
- **Hybrid.** Keep the pipeline motif (already pure shapes — circles, lines, an arrow marker) as
  shapes, and accept font/viewer variance for the wordmark text.

This plan **recommends the hybrid posture**, and part (1)'s sketch already encodes it. Reasoning:
the motif was always going to be shape primitives regardless of posture (the Spec JSON schema's
native content for a diagram-style banner), so shapes cost nothing extra there. The wordmark's
value is legibility and brand association, not pixel-identical cross-viewer fidelity — nothing in
the original Grok ask ("prioritize making it more approachable for new users") or GROK-04's fresh
evidence demands pixel-perfect rendering, only a real, git-trackable visual asset. A `sans-serif`
fallback keeps the wordmark legible on any viewer even under font substitution, which is a bounded,
low-severity risk for a discoverability asset, not a functional defect.

**Does converting text to shapes change v8.2's honest S-effort estimate? No, under the recommended
hybrid posture** — the motif was already shape-native, and the wordmark stays a single `text`
element, so part (4)'s decomposition is unaffected and **S is sustained**. **If a future
implementer instead required full text-to-shape conversion of the wordmark** (rejecting the hybrid
recommendation in favor of the pixel-identical posture), the answer flips to **yes**: effort would
move from **S to M**, because the font-to-path step falls outside `svg-precision`'s own
build/validate/render/diff contract and requires an external, non-mechanical tool or process —
qualitatively different work from "one Spec JSON, one build, one embed line."

above, which extracts `target='assets/hero.svg'` from a synthetic `![Hero banner](assets/hero.svg)`
line exactly as it would from a plain link. However, `_check_docs_file`'s resolution logic (lines
343-346, read this session) explicitly skips any link target whose `file_part` does not end in
`.md` via a bare `continue` — **before** the link is added to `total_links` or resolved against the
filesystem. A non-`.md` target such as `assets/hero.svg` therefore falls through this `continue`
silently: not validated, not counted, not flagged, regardless of whether the file at that path
actually exists.

pass `check-links.py`/VAL-03 unconditionally — CI provides **zero** safety net for this specific
link type, so the embed line and the `docs/assets/hero.svg` asset **must land in the same commit**
as a matter of author discipline, not because any gate enforces it. This is a **bound refinement of
