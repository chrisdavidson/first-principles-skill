## Methodology

This is v8.4's fifth exercise of the v8.0 closure clause "any future work is a fresh project
decision" (following v8.1 external-review triage, v8.2's re-investigation of v8.1's 19
not-approved items, and v8.3's technique/context-optimization evaluation). Where v8.3 identified
and ranked candidate optimizations as findings, this document renders the fresh go/no-go verdict
plus costed implementation-readiness plan that v8.3 explicitly deferred to a future milestone —
for the two v8.3-surfaced candidates named in this milestone's scope. The four governing
decisions, carried in intent from
[`150-CONTEXT.md`](../.planning/phases/150-implementation-readiness-evaluation/150-CONTEXT.md):

- **D-01 — Reuse v8.3's D-04 4-factor composite with factor 1 relabeled to "value."** The
  consolidated prioritized disposition (§5) reuses v8.3's [section 6](v8.3-technique-context-optimization-eval.md)
  D-04 4-factor composite with factor 1 relabeled from "context-savings" to "value" (scored 1-3).
  The remaining three factors — goal-fidelity-risk, byte-freeze-cost, implementation-effort — and
  the formula `value x (4 - risk) x (4 - byte-freeze) x (4 - effort)` carry over **byte-identical**
  from v8.3 §6; only the label and the scale definition of factor 1 change. Rationale: a
  savings-only axis provably cannot score a line-*adding* candidate — v8.3 itself excluded its own
  §4 #6 item on exactly that ground ("it would *add* lines, not save them — and is therefore not
  scoreable on the same savings-composite axis"). Relabeling makes line-savings one *kind* of
  value, so both a line-saving candidate (extraction) and a line-adding candidate (the banner) land
  on a single defensible ranking scale.
- **D-02 — The value scale is a superset that preserves v8.3's arithmetic.** v8.3's line-count
  thresholds (under ~50 lines is 1; ~50-150 is 2; 150+ lines or a headline lever is 3) remain the
  scoring rule for a savings-type item; non-savings value is anchored alongside on the same 1-3
  scale (3 = unblocks a stated top-priority ask / headline-level value). The extraction's savings-3
  therefore maps to value-3 **by construction**, and its composite must reproduce **24 exactly**
  (§5 shows this arithmetic explicitly, not merely asserts it — v8.3's published rank-4 score is
  reproduced under the relabel, never silently moved). Rationale: v8.3 is SHIPPED and its rank-4
  composite of 24 is a published number; a relabel that quietly moved it would put this document in
  contradiction with a shipped doc, which the project's no-contradiction convention forbids.
- **D-03 — Verdicts are independent of the composite; disagreement is flagged, not hidden.** The
  GROK04-01 (§1) and EXTRACT-01 (§3) GO/NO-GO verdicts are reached independently, purely on their
  own evidence — **never derived from the composite score**. The composite's only job is to *order*
  items within §5's consolidated disposition. If a verdict and the composite rank disagree (a
  NO-GO item outranking a GO item, or vice versa), §5 flags that disagreement as an explicit
  finding rather than silently listing items in composite order. Rationale: prevents a 1-3
  subjective scale from quietly deciding a build/defer binary — the false precision the project's
  honesty-not-score convention resists; a rank/verdict mismatch reads as an error to a future
  reader unless the document narrates it.
- **D-04 — Extraction's composite inputs are fixed from v8.3, plus an explicit sensitivity note.**
  The extraction's composite inputs are **consumed as fixed from v8.3** (value 3 / risk 2 /
  byte-freeze 2 / effort 2 = 24) — no re-derivation of v8.3's own analysis. §5 additionally carries
  an explicit sensitivity note covering two soft spots surfaced during scouting: (a) whether the
  `Handoff` section of each split reference file is procedural (core) or worked-detail (appendix) —
  if it stays in core, the four-file line saving drops from ~406 to ~285 against v8.3's claimed
  "400-600+", pressuring the value-3 score; and (b) no mechanism to load a `-detail.md` file
  currently exists (`{{PROCEDURE:slug}}` removal is free, but the on-demand deep-dive load surface
  would have to be built), pressuring the effort-2 score — and states in one line whether the final
  ordering survives that conservative reading.

## §1 GROK-04 Hero Banner — Verdict (GROK04-01)

**v8.2 cross-reference:** [`v8.2-grok-reassessment.md`](v8.2-grok-reassessment.md) section GROK-04
— disposition **promote-candidate** (non-binding input to a future fresh milestone decision, per
v8.2's own framing).

**Recommendation being evaluated:** Add a hero image/banner to the GitHub repo, authored via the
`svg-precision` skill.

**Fresh evidence (re-confirmed this session):**

```
$ test -d docs/assets && echo "EXISTS" || echo "ABSENT: docs/assets/ does not exist"
ABSENT: docs/assets/ does not exist

$ grep -rn 'hero\|banner' README.md docs/*.md

(no hits — no local-asset Markdown image embed exists anywhere in README.md or docs/*.md; the

$ grep -n 'badge\|shields\|img\.' README.md

```

`[VERIFIED: repo]` No `docs/assets/` directory exists. No hero/banner asset or local-asset Markdown
image embed exists anywhere in the repo. README.md's badge line is unchanged from v8.2's
observation — still exactly 4 badges (Validation, Version, License, Claude Code compatibility).
The banner would be the first image asset and the first local image embed of any kind in this
repo's history.

**Real feasibility:** The v8.2 unblock rests on the `svg-precision` skill's documented contract —
re-read this session at `~/.claude/skills/svg-precision/SKILL.md`: a strict Spec JSON is turned
into an SVG via `svg_cli.py build`, then `validate` (structural correctness), with optional
`render`/`diff` for a PNG preview. The skill is available in this session's toolset and is
genuinely sufficient for a typographic banner — it explicitly supports text elements alongside
shapes, and its own design rules flag the one relevant risk directly: *"Text varies by
fonts/viewers. If you need pixel-identical results, treat text as a risk and prefer shapes."*
Feasibility holds, with that specific caveat carried forward rather than assumed away — a
typographic banner (project name + a motif) is exactly the case the skill's own rules warn about,
so §2's spec should either accept font-rendering variance across viewers or convert the project
name to outlined shapes.

**Honest effort/cost:** v8.2 estimated **S** (one `docs/assets/hero.svg` file, one README embed
line). Fresh scrutiny of the concrete work items — one Spec JSON, one generated SVG, one README
embed line, one `check-links.py` scan-scope confirmation — **sustains S**, but refines the fourth
item beyond what v8.2 established. v8.2 confirmed only that `scripts/sync-content.py` has no
`assets` coupling (moot regeneration concern). This session additionally re-read
`scripts/check-links.py`'s scan globs directly: `FULL_CHECK_GLOBS`
(`first-principles/agents/**/*.md`), `NAMESPACE_ONLY_GLOBS` (`shared/**/*.md`), and
`DOCS_CHECK_GLOBS` (`docs/*.md`) — **none of these match repo-root `README.md`**. `[VERIFIED:
repo]` Root `README.md` is not scanned by `check-links.py` at all today, under any glob. This
means embedding the banner in README.md would build cleanly with zero required scan-scope work
(cheaper than v8.2's open "would need confirming" item suggested) — but it also means a broken
embed path would go uncaught by CI, a genuine gap v8.2 did not fully resolve. Net effect: cost
stays S; the fourth work item is not "confirm coverage" but "accept that README.md link integrity
is currently unchecked by any gate, banner or not."

**Byte-freeze relaxation cost:** Evaluated independently against all six frozen surfaces listed in
Scope & Invariants — detector marker counts, `MIN_HEADER_HITS`, `_COMPOSER_FOCUS_CEILING`, the
v7.8 guard column/tiebreaker, frozen baselines/captures, and the agent body. A new `docs/assets/`
file and a README.md edit touch none of them: `docs/assets/` is outside `shared/` and outside the
generated `first-principles/` tree, and README.md is outside the assembled agent body entirely.
Result: **None** — confirmed directly, not merely inherited from v8.2's finding.

**Value delivered:** Modest but genuine. This is the one item the external Grok review itself
flagged under High Priority (documentation/discoverability), and "prioritize making it more
approachable for new users" names exactly this kind of first-impression polish. Weighed honestly
rather than inflated: the repo already carries 4 status/compatibility badges and a full docs
navigation index (`docs/README.md`) — both already-shipped discoverability signals. A banner adds
visual/brand recognition, which is a real but narrower slice of "approachability" than the
original ask covered; most of that ask is already satisfied by prior work.

**Stress-test of the prior rationale:** Three pressure points tested against v8.2's
promote-candidate reasoning:

(i) *Session-local vs. repo-guaranteed feasibility.* `svg-precision` is a **user-level skill**
installed at `~/.claude/skills/svg-precision/` — outside this repository, not a repo-tracked
dependency, and not guaranteed present in every future session or for every future contributor.
v8.2 framed the feasibility unblock as durable ("a genuine rationale collapse, not a
reinterpretation"); fresh scrutiny narrows that claim. The *authoring* dependency is real and
session/user-local, not repo-guaranteed. The *artifact*, once built and committed as a static
`.svg` file, carries zero runtime dependency on the skill thereafter — GitHub renders SVG natively
with no plugin-side tooling required to display it. This weakens the unqualified "collapse" framing
without reversing the feasibility conclusion: feasibility is real for producing the asset now, not
guaranteed for regenerating or editing it later without the same skill available.

(ii) *Ongoing maintenance with no gate.* An SVG authored once via Spec JSON has no CI gate watching
its currency — if the project name, version, or pipeline framing changes, nothing forces a banner
update, unlike the badges (which point to live, self-updating sources: CI status, version file,
license file). This is a real, if low-severity, gap: a static banner is low-change-rate content,
and staleness risk is bounded, but it is not zero and no mechanism currently detects it.

(iii) *Additivity over the existing 4 badges and docs nav index.* Honestly modest. The badges
communicate status/version/license/compatibility; the docs index communicates structural
navigation; a banner adds a third, distinct signal — visual identity/brand recognition — that
neither existing surface provides. It is additive, not duplicative, but it is the smallest-value
increment of the three signals this repo now carries for a new visitor.

**Verdict: GO**

Feasibility is real (the skill is available and sufficient for a typographic banner, with the
font-rendering-variance risk named rather than hidden) and cost is honestly small (S, byte-freeze
cost None, confirmed independently this session). Value is modest but genuine and additive over
existing discoverability signals — the visual-identity gap the badges and nav index do not fill.
The stress-test qualifies v8.2's rationale (feasibility is session/user-local at authoring time,
not repo-guaranteed; no maintenance gate exists) without collapsing it: none of the three pressure
points changes the cost/value balance enough to flip the verdict. This GO is reached on this
candidate's own evidence, independent of any composite score (D-03) — the composite, authored in
§5, only orders items and plays no role in this determination.

§2 supplies the implementation-readiness plan — the concrete Spec JSON sketch, README embed point,
and acceptance criteria — under this GO verdict.
