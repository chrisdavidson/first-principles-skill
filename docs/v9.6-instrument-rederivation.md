## 1. Scope and Standing

**What D-01 asks for.** Three of this milestone's four Instrument requirements —
INSTR-01, INSTR-02 and INSTR-03 — appear already discharged by Phase 41 (backlog 999.120), because
the columns and the `_SELFAUDIT_CONTRADICTIONS` entry they name already exist in the shipped
`scripts/check-quality-harness.py`. "Appear" is not a disposition. D-01 requires this to be
re-derived rather than assumed: each requirement is split into its clauses (fixed by
`50-01-PLAN.md`'s interfaces block, ten rows total, ids `C-01-1`..`C-03-3`), each clause is mapped
to a named code site (symbol + line) and a named self-test control (function + letter) that would
fail if the clause regressed, and a verdict — discharged in full, in part, or not at all — is
recorded per clause rather than per requirement. Only the residue this re-derivation actually finds
becomes later work.

**The D-02 evidence standard, stated in full.** A clause reads **in full** only when both of these
hold: a named code site (symbol and line number, re-verified live at this record's phase base) AND
a named self-test control (the function housing it, plus its lettered sub-check) that would fail if
the clause's own behaviour regressed. A clause reads **in part** when a code site exists but either
no control names it, or the control that does exist does not actually exercise the clause's own
behaviour — a plausible-looking control that never runs the code path is the same gap as no control
at all. A clause reads **not at all** when no code site exists. **A clause with a code site but no
control is "in part," never "in full," regardless of how obviously correct the code looks** — this
rule is not softened anywhere in this record.

**Citation frame.** Every line number this record cites in `scripts/check-quality-harness.py` or
`scripts/check-traceability.py` resolves in phase base `30b5971` — both the full
`scripts/check-quality-harness.py:<N>` form and the abbreviated `:<N>` form. The frame is not the
reader's checked-out tree. The harness grows as later commits land, so the same number read against
HEAD points at an unrelated line. A citation is read with `git show 30b5971:scripts/check-quality-harness.py`,
piped to `sed -n` at the cited line, written inline in backticks. A citation in any other frame names
its commit on the same line — §3.1's R-50-01 row is the one such case, in frame `613febb`. The
symbol is the durable identity; the line number is a frame-scoped pointer to it.

explicitly does **not** govern INSTR-04 (the `reference_reads` census) — INSTR-04 is unbuilt at the
time of writing and is the subject of this phase's plans `50-02` and `50-03`, not this plan. Nothing

**The naming question, addressed explicitly (per the plan's own instruction).** The requirement
says "verdict blocks"; the shipped columns say "bands" (`selfaudit_bands_parsed`,
`selfaudit_offvocab_bands`). Is the gap cosmetic or semantic? `_selfaudit_band_census`'s matching is
driven by `_SELFAUDIT_CRITERION_WIDE_RE`, which finds one occurrence per criterion **head**, not per
enclosing Markdown block — so, as the plan's own hint anticipates, a document carrying one block
that states all six criteria and a document carrying six single-criterion blocks are read
identically by the census (both produce up to six per-criterion entries). Because the shipped
rubric shape always emits one bold criterion head per criterion regardless of block grouping, "one
verdict block" and "one recognized criterion head" are, in the wording sense, the same thing in
practice: the column counts one entry per criterion assertion, which is what "verdict block" means
in this repository's own rubric. **This is cosmetic, not semantic** — the measured thing (a
recognized per-criterion verdict statement) is identical to what the clause names; only the field
name ("bands" vs. "blocks") differs, and per the Deferred Ideas / D-03 rule this is never a rename
task. The one genuine granularity nuance — that `selfaudit_bands_parsed` alone counts only the
in-vocabulary subset, and the *total* recognized-verdict-block count is the sum of
`selfaudit_bands_parsed` and `selfaudit_offvocab_bands` — is noted above under C-01-1/C-01-2's
verdicts rather than treated as residue, because `(P9)` demonstrates a reader can recover the total
from the two named fields and the split is itself the useful signal 999.120 H3 was built to add.

## 4. Re-deriving anything further

A future phase that wants to re-derive a requirement against shipped code — as this record does for
INSTR-01..03, and as Phase 52 is scheduled to do next for OBS-02 (roadmap ordering constraint 4) —
follows the same procedure this record applied:

1. **Split the requirement into its clauses.** Use the requirement's own filed wording (the
   `.planning/REQUIREMENTS.md` bullet, or its ROADMAP success-criteria phrasing where the
   requirement spans several). Each clause should be independently checkable — a single code site
   and a single control should be able to falsify it on its own.
2. **Map each clause to a named code site.** A symbol and a line number, re-verified live at the
   re-derivation's own phase base (never trusted from a prior document, a CONTEXT.md canonical-refs
   list, or training-time memory) — this record's own §1 correction (`render_defect_incidence` →
   `run_detect_defects`) is the demonstrated reason why.
3. **Map each clause to a named control.** The function housing it, plus its lettered sub-check, and
   confirm the letter is real by grepping the live file, not by trusting a docstring's stated range.
   §2.2's correction (the `_selftest_defects` docstring literally names only `(P1)`, `(P9)`,
   `(P10)`-`(P13)`, not every individual `(P2)`-`(P8)`) is the demonstrated reason to verify the
   letter's existence against the function's own body, not merely its docstring's stated ranges.
   State that frame once, in the record's own `**Citation frame.**` paragraph, and name any other
   commit frame inline on the citing line — this record's own §3.1 R-50-01 row is the demonstrated
   reason: a frame-less line number written at one commit went stale within two commits.
4. **Apply the D-02 rule without softening it.** A code site with no control, or a control that does
   not exercise the clause's own behaviour, is "in part" — never "in full," regardless of how
   obviously correct the surrounding code looks.
5. **Record the verdict** here, in a record of this record's own shape, or in a dedicated successor
   record if the requirement population is large enough to warrant its own note (as Phase 52's
