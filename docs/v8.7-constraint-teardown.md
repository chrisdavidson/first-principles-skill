## 1. Scope and Standing

This is a **named standing rule**, not a one-off v8.7-scoped exception. It carries no expiry
date. A future milestone reads this record the same way it reads
[`v8.0-final-closure.md`](v8.0-final-closure.md) — as a durable disposition, not a temporary
grant that lapses when v8.7 ships.

The rule is a **subtraction record against a default-frozen baseline**. Anything not explicitly
listed in §2 below remains frozen and gating by default. Silence never means permission — a
future milestone that wants to touch something not named in §2 must author its own successor
record per the procedure in §4, not read this document's silence as authorization.

This record's scope did not originate from a previous milestone's own paperwork — it derives
from the 2026-07-22 `.planning/ALTITUDE.md` constraint audit, which re-examined nine carried
constraints against evidence rather than inheriting them by default. Five were found invalidated
and are retired below; four survived and are restated in §3 as still frozen.

## 2. What Is Retired

Exactly five items. No more.

**1. The 644-line body-budget gate.**

The gate is retired; the figure is not. `scripts/check-body-budget.py` still reports the
generated agent body's current line count on every run, but it no longer fails a commit or a
battery run because of that count. The evidence: the script's own fitted-limit provenance
comment — "limit raised to 622 + 22 buffer" — records that the number was recalibrated whenever
it bound, across the raise chain 500 → 580 → 644, rather than derived from any measured quality
requirement. `docs/v8.6-quality-ab-experiment.md`'s blind A/B is the null result that confirms
the fitted number carried no quality signal: a 590-line body and a 612-line body — a 22-line
contrast, the exact size of the "buffer" the limit was raised to protect — scored identically,
both arms 2/3 PASS, band total 35 each, with failures tracking the problem rather than the arm.

Name the irony plainly: v8.6 spent a whole milestone compressing the agent body to buy back
22 lines of headroom under a budget this record now retires, and that same milestone's own A/B
experiment is the evidence that the 22 lines did not matter. What survives: the figure is still
reported — on every `check-body-budget.py` invocation and on every
`check-firewall-battery.sh` run, as an un-tallied `[INFO]` line — because Phase 165 needs the
body's growth to stay visible even though nothing will block it.

**2. The `_COMPOSER_FOCUS_CEILING` freeze — the freeze only.**

The value stays 4. This record grants permission to change `_COMPOSER_FOCUS_CEILING` under a
successor procedure (§4); this phase performs no retune. The evidence:
`docs/v8.6-live-remeasure-verdict.md`'s Phase 160 S-P03 run5 finding, which shows the ceiling
actively penalising fidelity rather than merely gating noise — run5 fired the highest fishbone
marker count of the five runs measured (4 distinct markers, more than any of runs 1–4) and was
still scored a miss, purely because its `composer_hits` count reached
`_COMPOSER_FOCUS_CEILING`. The run that most closely followed the expected template was the one
the ceiling suppressed.

Record honestly: dropping the literal drift guards on the constant does not by itself make it
freely editable in practice. RR-77-08's surviving relative check
(`_rr7708_composer == _COMPOSER_FOCUS_CEILING - 1`) compares an adversarial fixture's
`composer_hits` count against one below the ceiling, and that fixture's hit count is fixed at 3
in the sentinel's own source. A future retune of `_COMPOSER_FOCUS_CEILING` is therefore a
two-part edit — the constant itself and the fixture that proves it is load-bearing — and a
successor record must say so rather than assume changing one constant is sufficient.

**3. K-of-5 Step 0 as a phase gate.**

K-of-5 Step 0 results are recorded observations from here forward; they may not gate a phase.
The evidence: the S-P04 (five-whys) vector 2/5 → 0/5 → 2/5 across v7.11, v8.5, and v8.6 — a
value that swung across the pass/fail line twice with no source change to the five-whys
technique between those measurements that would explain the swing. At N=5, noise equals effect;
a single flipped run moves the recorded K/N by 20 percentage points, which is not a resolution
either direction can be read as durable.

What is demoted is the **authority of the number**, not the tool. `scripts/check-step0-live.py`
is untouched by this phase: it keeps `--min-pass` and its verdict line, because every frozen
baseline from v7.4 through v8.6 and every documented invocation depends on that comparability
staying intact. A future milestone that reruns the harness still gets a K/N and a PASS/FAIL
verdict line from the tool itself — what changes is that this record, and the docs that follow
it, no longer treat that verdict as a gate a phase must clear.

**4. The gitignored-and-unrecoverable posture of one strategic-record path — `matrix.json` only.**

`.planning/phases/82-traceability-matrix-and-gap-findings/matrix.json` is un-ignored by a targeted
`.gitignore` negation (Plan 03 of this phase); `.planning/` stays ignored otherwise, and
`.planning/ALTITUDE.md` specifically **remains ignored and untracked** — its un-ignore is deferred,
not performed, by this phase (see the disposition below). `matrix.json` is tracked as a committed
artifact rather than left to regeneration — regeneration produces a fresh matrix, not
recoverability of the specific frozen artifact that the `phases.clear` workaround (item 5, below)
existed to protect.

> **Amendment (2026-07-28, post-v8.13).** The artifact has been relocated to `docs/data/matrix.json`
> and `.gitignore` restored to a blanket `.planning/` rule. Nothing about item 4's substance
> changes: the matrix JSON is still tracked, still recoverable from `phases.clear`, still
> byte-identical (`ee373f6a`). What changes is the *mechanism* — durability is now obtained by
> keeping the artifact outside `.planning/` rather than by punching a negation chain through the
> ignore rule. This is item 4's own point 2 applied to its own implementation: durability was the
> goal, and the negation chain bought durability at the cost of putting a `.planning/` path on a
> public repo, which was never the goal. The `emit` invocation in `CLAUDE.md` and `docs/TESTING.md`,
> the banner emitted into `docs/requirements-matrix.md`, and the module docstring were updated to
> the new path. The `.planning/ALTITUDE.md` deferral below is unaffected.

**The D-12 disposition (`.planning/ALTITUDE.md`) — challenged and deferred at the Plan 03
checkpoint, not exercised.** D-12 as originally recorded argued that publishing
`.planning/ALTITUDE.md` verbatim was "consistent with... a repo that already publishes failing
measured results and ACCEPTED-FINAL limitations." At the Plan 03 blocking checkpoint this argument
was challenged and the challenge held, for reasons recorded here in substance rather than by
reference to a since-resolved checkpoint:

1. The argument is an analogy that does not hold. Publishing failing measured results and
   ACCEPTED-FINAL limitations are claims about the *artifact's measured behaviour* — the
   honesty-not-score discipline (D-01 global) that governs them was built to stop the project
   flattering a measurement. `.planning/ALTITUDE.md` is not a measurement; it is a *strategic
   self-assessment*. Extending honesty-not-score to strategic self-criticism was asserted in D-12,
   not argued.
2. The load-bearing error underneath the analogy: **durability was conflated with publicity.**
   TEARDOWN-03's actual goal is that these artifacts be *recoverable* from `phases.clear` —
   recoverability requires version control, not publicity. Publicity is an incidental consequence
   of this repository being public; whether durability was obtainable without it was never asked.
3. Item 5's own citation names `matrix.json` alone as the cause of the `phases.clear` workaround.
   Tracking `matrix.json` alone therefore genuinely retires that workaround — `.planning/ALTITUDE.md`
   was never that cause, so its durability does not need to move for item 5 to be true.

**Disposition: DEFERRED, not resolved.** `.planning/ALTITUDE.md` remains gitignored and untracked
after this phase. TEARDOWN-03 is satisfied only in part by this record — `matrix.json`'s
recoverability is done; `.planning/ALTITUDE.md`'s recoverability is an open question left to be
decided later on durability grounds, not doctrine grounds. Per §4's successor procedure and this
record's own "silence never means permission" rule: this deferral is not itself authorization to
publish `.planning/ALTITUDE.md` later without a fresh, explicit decision — a future milestone that
wants to track it must make that call again, on its own evidence, not read this paragraph's silence
as having already decided it.

**Resolution (2026-07-24, at the v8.9 milestone close): ordinary-loss risk accepted on the record.**
The durability question this paragraph left open was carried as a standing todo
(`altitude-md-durability-open-question.md`) and is closed here by the fresh, explicit decision §4
requires — not by inference from the deferral above. The user accepts the ordinary-loss risk:
`.planning/ALTITUDE.md` remains gitignored, untracked, and unbacked, and its permanent loss to
accidental deletion or disk failure is an accepted, on-the-record risk rather than a further
deferral. No durability mechanism (an external copy, a private mirror, an encrypted committed blob,
or tracking) is adopted. This decision accepts the *loss* risk only; consistent with §4 it is **not**
authorization to publish or track the file — any future change to that posture still requires its own
fresh, explicit decision. This records durability, not doctrine: the Plan-03 challenge (durability was
conflated with publicity) stands unchanged; what is settled now is only that the un-mitigated loss
exposure is knowingly accepted rather than left open.

**5. The `phases.clear`-stays-OFF workaround.**

Retired by record only. There was never a `phases.clear` config key in
`.planning/config.json` — this was always a behavioural rule contributors followed, not a flag
that could be flipped. Retiring it is therefore a documentation act: no config key changes and no
phase directory is cleared anywhere in this phase. Its cause — `matrix.json` being an
unrecoverable gitignored artifact — is removed by item 4 above; once the artifact is tracked,
the workaround that existed to avoid destroying it has nothing left to protect against.

## 4. Retiring Anything Further

A future milestone that wants to retire or relax anything beyond §2 must follow this procedure:

1. **Name the specific constant, sentinel, gate, or disposition** to be retired or relaxed — no
   broad or ambiguous grants.
2. **State the measured evidence** motivating the change — the same honesty-not-score discipline
   this record follows.
3. **Author a successor governing record** that names this document and states exactly what it
   supersedes.
4. **Leave this record byte-intact.** In-place edits to a prior milestone's terminal or governing
   record are never an acceptable substitute for a successor record.

Restated: silence never means permission. A future milestone finding this document silent on a
constraint it wants to touch must treat that silence as "still frozen," not as an oversight to
exploit.

## 5. Battery Composition and Known Stale Surfaces

**Composition change.** `scripts/check-firewall-battery.sh`'s offline gate tally moves
**16 → 15** (16 tallied gates to 15 tallied gates) — the drop is the body-budget gate, which is
now an un-tallied `[INFO]` line (`[INFO] body-size`) rather than a `gate()`-tallied PASS/FAIL
entry. The battery's own header comment names this change explicitly; a green run at an
undeclared count would be a regression this record exists to prevent.

**Surfaces this phase deliberately does not edit**, each with its reason:

- `scripts/install-hooks.sh` (line 57) mentions the body-budget gate in its own prose.
  `scripts/smoke-test-hook.sh` is stronger — it is an end-to-end test that *asserts* the hook
  rejects an over-budget commit (step (c): `git commit` must be rejected and stderr must name the
  budget violation), an assertion TEARDOWN-01 makes permanently unsatisfiable now that the hook no
  longer rejects on size. It is additionally already inert for an unrelated, pre-existing reason:
  its own `MAX_LINES=500` pre-flight check aborts against the current 590-line generated body.
  Neither script is named by this phase's decisions (D-01..D-14), and neither is wired into CI, the
  offline battery, or pytest. Both are recorded here rather than edited because silence never means
  permission runs in both directions — not editing them is a deliberate choice, not an oversight,
  and Phase 167's repo-wide sweep is where they get reconciled.
- `scripts/check-step0-live.py`'s printed frozen-constants summary and `--min-pass` verdict line
  — the tool is deliberately untouched (§2 item 3); what changed is the authority given to its
  output, not the output itself.
- `README.md`, `CONTRIBUTING.md`, `docs/CONFIGURATION.md`, `docs/ARCHITECTURE.md`, and the
  historical `docs/` verdicts (`docs/v8.6-measured-reduction.md`, `docs/history/**`, and prior
  milestone verdicts) — Phase 167's repo-wide sweep (CLOSE-01 criterion 2) is where the broader
  prose reconciliation happens. Historical documents are not rewritten here — they record what
  was true when they were written, and rewriting them would falsify the historical record rather
  than correct it.
