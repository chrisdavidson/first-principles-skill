# v8.18 PRAOR Loop Closure

**Milestone:** v8.18.0
**Recorded:** 2026-08-29
**Status:** Frozen evidence. This record is a measurement and a narrative true of its date — what
the 2026-08-27 review found, how each finding was closed, and what shipped as a result — not a
rule in force. Nothing here gates a future milestone the way
[`v8.7-constraint-teardown.md`](v8.7-constraint-teardown.md) gates constraint retirement or
[`v8.14-delivery-verification.md`](v8.14-delivery-verification.md) gates Phases 189-191. A future
contributor who wants to change how the Act limb, the Observe→Perceive edges, or focused-mode
parity work is not asking this document's permission; they are producing new evidence of their
own, which is exactly the posture `docs/README.md`'s adjudication section assigns to frozen
evidence rather than to a governing record.

---

## 1. The review

On 2026-08-27, a review mapped the agent body — `shared/spine/SKILL-body.md` and its
companion files — against the Perceive → Reason → Act → Observe → Report loop the project's core
value depends on: *an analysis the agent produces must be auditable by a skeptic without asking
the analyst anything*. Perceive, Reason, and Report scored strong. Observe scored strong on its
own terms but was purely introspective — the Self-Audit Gate scores the analysis document's own
internal structure, never an outcome the agent produced in the world. Act was absent outright.
The consequence stated plainly: the loop closed *inside the document* the agent wrote, never
*through the environment* it was supposedly analyzing. A ground truth could carry a citation with
nothing behind it, a validation failure had nowhere to route, and a slash-invoked focused skill
could stop short of the loop the full composer completed. That review produced all four gaps
below; nothing else did.

## 2. The four gaps

### Gap 1 — No Act limb

Phase 3 of the five-phase methodology could label a ground truth's provenance, but the procedure
never prescribed a step that actually opened the cited source. `Read`, `Grep`, and `WebFetch` were
already permitted by the frontmatter — only `Write`/`Edit` are disallowed — so the tools existed
and nothing in the written procedure told the agent to use them for evidence. The
Self-Audit Gate's Criterion 3 named a `read-at-source` provenance test whose satisfying branch
did not exist anywhere the agent could reach it: a ground truth could be labelled `read-at-source`
with nothing the procedure did to earn that label, or the rubric could flag it and have no
prescribed remedy beyond a downgrade. Requirements ACT-01 through ACT-04 cover the missing step
itself — what it does, how provenance is assigned from what was actually read, how an
unreachable source is recorded rather than silently dropped, and how the step is bounded so it
cannot consume the turn budget the Self-Audit Gate needs. Phase 1 (Evidence Acquisition) closed
this, gated by HARN-01 (`scripts/check-act-limb.py`).

### Gap 2 — Unreachable evidence rule

A direct consequence of Gap 1, tracked separately because it lives in the rubric rather than in
Phase 3's procedure: Self-Audit Gate Criterion 3's Fix branch named "acquire the evidence" as an
option with no step anywhere in the methodology that performed acquisition. A rule that names a
remedy no prescribed step can execute is not a real remedy — it reads as available but resolves
to nothing every time. Requirement ACT-05 closes this: Criterion 3 now names both Fix
branches — acquire the evidence, or downgrade the confidence — and states that acquisition is
preferred when the source is reachable, so the gate stops resolving only toward the weaker
output by default. Phase 1 closed this alongside Gap 1, gated by the same HARN-01.

### Gap 3 — No Observe→Perceive edge

A Criterion 1 Absent verdict — the Self-Audit Gate's judgment that the Essence Statement itself is
missing or unsupported — had no named, bounded route back to Phase 1 to re-frame that statement,
and no route to re-open input via `AskUserQuestion` once the analysis was already underway. The
clarification policy in `shared/agent/input-contract.md` scoped `AskUserQuestion` to the start of
a run only, so a mid-run discovery that an input was missing had nowhere to go. Without a bounded
return edge, "Observe" was a dead end rather than a loop-closing limb: a failing verdict produced
a diagnosis and nothing the procedure did about it. Requirements LOOP-01 through LOOP-05 cover the
re-entry route itself, the widened `AskUserQuestion` scope, the bound on re-perception passes
(so the Fix/Repeat loop cannot spin against `maxTurns: 60`), Phase 3's exit-criterion wording no
longer contradicting the new edges, and the requirement that a fired edge is recorded so a reader
can tell a revised analysis from a first draft. Phase 2 (Loop Closure) closed this, gated by
HARN-02 (`scripts/check-loop-closure.py`).

### Gap 4 — Focused-mode divergence

The 13 slash-invocable companion skills (`shared/skills/<slug>/SKILL.md`) each stopped at the
named technique's raw output — a fishbone diagram, a set of five whys, a trade-off table — with
no validation step and no Observe limb, while the agent's own internal `focused-<technique>` mode,
reached through the full composer, completed the loop. A user invoking `/first-principles:fishbone`
directly got a materially different, shorter loop than one who reached the same technique through
the agent, with no documented reason for the difference. Separately, Step 0's execution-branching
parenthetical — the text stating which phases run under focused mode — did not name Validate at
all, so even the internal focused branch's own documentation understated what it did. Requirements
PAR-01 through PAR-03 cover parity itself (same loop, or a stated evaluable reason for divergence),
the scope-proportionate validation step now emitted into every stub, and Step 0 naming Validate.
Phase 3 (Focused-Mode Parity) closed this, gated by HARN-03 (`scripts/check-focused-parity.py`).

## 3. Dispositions

Each gap: closed, with the gate that proves it and the negative-control posture measured behind
that gate. Read these as structural guarantees — the named prose is present, well-formed, and
cannot be silently stripped — not as live-behaviour measurements of what the agent actually does
on a given run. That distinction matters enough to restate: MEAS-01 (a live harness for whether
the agent performs the Phase 3 read when a source is reachable) and MEAS-02 (a quality-harness A/B
measuring whether evidence acquisition changes analysis quality) both remain deferred v2
requirements, deliberately not attempted in this milestone.

- **Gap 1 + Gap 2 (Act limb, evidence rule)** — closed by Phase 1, gated by **HARN-01**
  (`scripts/check-act-limb.py`). Every one of HARN-01's `failures.append(...)` assertion sites was
  measured, individually, unable to survive a targeted neutralization of the prose it guards — 0
  of 58 sites survived the plan's own whole-file audit, with a dedicated negative control proving
  each one. This is a structural gate: it asserts the prescribed step and its bound are present
  and well-formed in the emitted agent body, not that the agent takes the step on any particular
  run.
- **Gap 3 (Observe→Perceive edge)** — closed by Phase 2, gated by **HARN-02**
  (`scripts/check-loop-closure.py`). 47 negative controls back its assertions, each independently
  measured able to fail when the re-entry edge, its bound, or its firing record is stripped from
  either `shared/spine/SKILL-body.md` or `shared/agent/input-contract.md`. Re-verification on
  2026-08-28 independently re-derived every gap against the live tree — including fresh, hand-built
  mutations fed directly to the gate's checker functions — rather than accepting the fix report on
  its word.
- **Gap 4 (focused-mode divergence)** — closed by Phase 3, gated by **HARN-03**
  (`scripts/check-focused-parity.py`). 0 of 58 `failures.append(...)` assertion sites survived a
  message-preserving whole-file neutralization audit run with no exclusions (the gate's own
  `Stub-0` site included), cross-checked against an independent `if False and ...` reviewer
  operator that agreed on every site. This is the largest of the three new gates by assertion
  count and by iteration: it took plans 03-03 through 03-08 (six plans) to close every gap a
  succession of audits, a verification pass, and a UAT pass found in its own control coverage —
  recorded honestly here rather than folded into a single clean narrative, because the repeated
  audit findings are themselves part of what "0 of 58 survived" means: the number is the end state
  of several rounds of finding and closing gaps, not the first draft's result.

## 4. What shipped

Beyond the four closures above, this milestone shipped the release mechanics that make them
reachable and durable:

- **HARN-04** — HARN-01, HARN-02, and HARN-03 are registered in
  `scripts/check-firewall-battery.sh` as three single-command `gate "HARN-0N" ... --self-test`
  calls, moving the offline battery's tally from **17 → 20**. Each self-test already carries a
  live positive control over the real emitted tree, so no separate live invocation was added
  alongside the self-test call — a second invocation would have asserted nothing new. All three
  gates also gained a CI job in `.github/workflows/validation.yml`, so a pull request that
  regresses any of the three fails in CI, not only in a local battery run a contributor might
  skip.
- **SHIP-06** — `bash scripts/check-firewall-battery.sh` now reaches `FIREWALL: GREEN` under the
  repository's bare `python3`, with no `uv run` wrapper. This was already discharged during Phase
  3 by plan 03-08, ahead of Phase 4: VAL-03's third leg previously shelled out to `python3 -m
  pytest`, and the bare `python3` on this machine cannot import pytest, which the battery reported
  as a genuine `FIRE­WALL: RED` gate failure — indistinguishable from an actual link-check
  regression. `resolve_pytest_python()` now tries `.venv/bin/python3` first, then `python3`, each
  confirmed by an `import pytest` execution preflight, and a `gate_prereq()` wrapper reports an
  unmet prerequisite as a third, distinguishable outcome — `FIREWALL: BLOCKED`, exit 2 — that can
  never be confused with `GREEN` (a real pass) or `RED` (a real gate failure, which still outranks
  a missing prerequisite even when both conditions are present at once). Phase 4's own remaining
  share of SHIP-06 was to *verify* this held after regeneration and the version bump, not to
  implement it again.
- **All 17 hand-maintained version stamps** moved from `8.17.5` to `8.18.0` in lockstep — the 14
  `shared/skills/<slug>/SKILL.md` sources, `shared/spine/SKILL.meta.yml`, and the two
  out-of-generator-scope manifests (`.claude-plugin/marketplace.json`,
  `first-principles/.claude-plugin/plugin.json`), the last two hand-edited as the pre-documented
  sanctioned exception to the never-hand-edit-the-generated-tree rule. `check-version-stamps.py`
  reports all 17 at `8.18.0`; regeneration was proven idempotent by an `md5sum` diff over the full
  `first-principles/` tree taken before and after a second `sync-content.py --write` run.

## 5. Traceability

The v8.18 milestone registered all 23 of its own requirements as rows in
`scripts/check-traceability.py`'s matrix — `_rows_v818()`, the first **v8.x** milestone requirement block added since v7.9 — the v7.11
block (`_rows_v711()`, 11 audit-only rows, Phase 131 RECON-03) is the last addition before it. The
23 rows tier **21 reproducible / 2 audit-only**: SHIP-04 and SHIP-05 have no
re-runnable gate behind them — a milestone record and a CHANGELOG entry are read, not executed —
so they sit in the audit-only tier by the same rule every other unreproducible requirement in the
matrix follows, while the remaining 21 (ACT-01..05, LOOP-01..05, PAR-01..03, HARN-01..04, SHIP-01,
SHIP-02, SHIP-03, SHIP-06) are each backed by a script that can be re-run to confirm them. This
tier partition is pinned by exact `bare_id` set inside a dedicated `V818-ROWS` sentinel
(`_self_test_v818_rows_sentinel()`), mirroring the shape of the pre-existing `_self_test_v79_rows_sentinel`
with two adaptations: the tier is pinned by ID rather than by count alone, and deep-link
resolution is restricted to the 21 reproducible rows plus a positive empty-link check on both
audit-only rows. Each of the sentinel's seven assertions was measured, individually, to stop
printing its own PASS line when neutralized, and six hand-built data mutations (a tier flip, a
tier swap, a bogus audit-only link, a dropped row, a wrong milestone label, a lowercase
capability string) were each caught by name by the assertion that owns them.

`build_matrix_rows()` now returns **237 rows total** — up from 214 — moving the coverage headline
from **126 reproducible / 88 audit-only / 0 gap / 214 total** to **147 reproducible / 90
audit-only / 0 gap / 237 total**. This is a stated departure from the historical Phase 142 D-01
note, which reasoned that no further milestone requirement block should register matrix rows once
the project's "final" v8.0 accounting had shipped; that note is left byte-intact in
`docs/requirements-traceability.md`, with a dated addendum immediately beside it recording the
departure and its own reasoning rather than editing the note to fit the new decision. The
discriminator that licenses the departure: v8.18's 21 reproducible requirements are each backed by
a deterministic offline gate that can be re-run to confirm them — the first requirement block
since v7.9 to carry that property — where the requirement blocks the D-01 note was written to
guard against were paperwork-only additions with nothing re-runnable behind them. `docs/data/matrix.json`
and `docs/requirements-matrix.md` were both regenerated via the `emit` subcommand and confirmed
byte-identical on a third consecutive run, proving the regeneration itself is idempotent.

## 6. Standing records changed

Two standing records changed as a direct consequence of this milestone reaching its coverage
headline, neither edited silently:

- **`docs/v8.0-final-closure.md`'s immutability trait is lifted.** That document had described its
  own coverage figures as kept deliberately untouched on the reasoning that rewriting them would
  falsify the historical record of what v8.0 measured. The trait's premise — that v8.0 wrapped the
  project and no further milestone would touch the headline — expired the moment work continued
  past v8.0 and the headline moved a first time. By this milestone the headline had already moved
  three times (133/96/0/229 → 132/97/0/229 at the v8.8 post-close re-tier → 126/88/0/214 when 15
  builder requirements were retired → 147/90/0/237 here), and the document's own §4 superseded-by
  language and standing banner were updated to state the current figure and the current battery
  tally (20/20), while the document's own v8.0-dated measurement (133/96/0/229, battery 15/15) was
  left untouched as the specific historical fact it records. A new dated addendum, appended at the
  end of the file in the same shape as its existing 2026-07-19 FREEZE-02 addendum, states the lift
  explicitly and separates what changed (current-state claims) from what stays frozen (the v8.0
  measurement itself).
- **`CHANGELOG.md`'s `## [8.17.2]` entry** carried a coverage-headline bullet stating
  `126/88/0/214` as the real figure superseding the stale `v8.0` figure it was correcting — accurate
  when 8.17.2 shipped, now itself superseded by this milestone's `147/90/0/237`. Rather than edit
  the historical entry to read the new number, a dated inline correction blockquote was appended
  immediately after it, naming the original figure, the date of the correction, and pointing at
  this milestone's own `## [8.18.0]` CHANGELOG entry as the place the immutability-trait lift
  itself is recorded as a v8.18.0 policy change in its own right.

## 7. What was deliberately not done

Barred, not unnoticed. Each item below has a stated reason it was not pursued in this milestone,
and a stated trigger for reconsidering it — the same posture `docs/README.md` uses for its own
post-v8.11 scope gate.

- **A registration-completeness guard** — a gate that would assert every requirement this project
  claims complete has *some* re-runnable check behind it, catching the exact shape of gap this
  milestone's own HARN-04 work closed by hand. Deferred: building it now would be
  apparatus-about-apparatus, barred by the standing post-v8.11 scope gate (`docs/README.md`,
  "Post-v8.11 state") and adjacent in kind to GREENMEAN-01's own WON'T-DO closure on
  battery-integrity scope — the class of check this project is best positioned to build is
  exactly the class its own scope gate forbids it from building absent a real trigger. Its named
  admission trigger: a GREEN battery discovered to have shipped over a defect that reached an
  install, the same evidentiary bar GREENMEAN-01's four measured instances already establish as
  real and recurring.
- **The focused-mode Act limb** — Phase 3 closed focused-mode's validation-step and Observe-limb
  divergence (PAR-01/PAR-02), but did not extend the Act limb's evidence-acquisition step into the
  13 slash-invoked stubs; that step lives only in the full composer's Phase 3. This divergence is
  itself the kind PAR-01 permits — documented with a stated, evaluable reason (a slash-invoked
  focused skill's narrower scope) — but it is still open, not closed, and is recorded here so a
  future reader does not assume Gap 1's closure reached the stub surface.
- **MEAS-01 and MEAS-02** — both remain deferred v2 requirements. MEAS-01 (a live harness for
  whether the agent actually performs the Phase 3 read when a source is reachable, as opposed to
  HARN-01's structural question of whether the step exists) is deferred because K-of-5 live
  results are recorded observations, never gates, per the standing governing record — building the
  harness now would need its own baseline freeze with no immediate consumer. MEAS-02 (a
  quality-harness A/B measuring whether evidence acquisition changes analysis quality relative to
  a confidence downgrade) is deferred until the behavior has shipped and produced something to
  measure, which this milestone is the first to make possible rather than the one that measures
  it.
